- 목적: **설계 검증을 백엔드 구현보다 먼저 수행**한다. 사용자가 실제 화면/동작을 확인하여 구조가 적합한지 판단한다.
- 적용 기준: 개인 [AGENTS.md](../../AGENTS.md) / [애자일 작업 기준](../07-agile-development-workflow.md).

## 화면 시안 위치

- `frontend/public/ui-review.html`: React 또는 FastAPI 설치 없이 열 수 있는 **정적 HTML/CSS/JS 퍼블리싱**.
- `frontend/public/bid-detail-review.html`: 목록에서 `전체 상세·제출·낙찰 관리`를 눌러 들어가는 **공고별 전체 상세 화면**. 독립 실행 시 `bid-detail-review.html?notice=m1`로 선택 가능.
- 기본/참가자격/RFP·평가/제출 관리/낙찰·점수/진행 이력 화면을 조작할 수 있다. 모든 수기 기록은 현재 탭 메모리 안에서만 유지한다.
- Vite를 설치·실행한 경우 `/ui-review.html`로 접근 가능하며 빌드시 `dist/ui-review.html`로 복사한다.
- 직접 다운로드해 브라우저로 열어도 사용 가능하다. **실제 나라장터·Google·모델·백엔드에 연결하지 않는다.**
- 기존 `frontend/src/App.tsx`는 초기 API 연결 샘플로 남아 있지만 **현재 우선 검토 대상은 독립 시안**이다.

## 설계 검증을 위한 화면/사용자 동선

| 화면 | 주요 행동 | 검증할 설계 판단 |
|---|---|---|
| 공고 탐색 | 공고 목록·검색어·AI/SW/DATA 필터 | 목록에서 핵심 정보가 충분히 보이는가 |
| 공고 상세 | 항목 선택 → 기술/요건/미확인 상태 표시 | 원문·법적 적격성 미확인을 명확히 이해하는가 |
| 임시 검토 보관함 | 보관함 추가 → 목록으로 이동 | 저장 동선이 필요한가, 목록과 상세의 구조가 적절한가 |
| 화면 검증 | 검토 항목을 직접 체크 | 무엇을 우선 개선할지 합의할 수 있는가 |
| 비정상 상태 | 0건/오류 선택 | 혼동하지 않고 재시도 또는 필터 변경을 이해하는가 |
| 반응형 | 휴대전화와 PC에서 메뉴/목록/상세 확인 | 작은 화면에서 상세 확인 및 탐색이 편리한가 |

## 검증 절차

1. PC/모바일에서 `ui-review.html`을 연다.
2. 검색어 `FastAPI`, AI 카테고리를 선택하여 검색 결과를 확인한다.
3. 첫 결과에서 `전체 상세·제출·낙찰 관리`를 선택한다. 기본정보, 참가자격, 제안서/평가, 제출 기록, 낙찰/점수, 진행 이력 탭을 차례로 확인한다.
4. `제출 관리`에서 제출 확인 단계와 제출 여부를 임의 값으로 입력하고, `낙찰·평가점수`에서 점수와 만점을 시험 입력한다. 실제 업체·접수증·기밀 정보는 넣지 않는다.
5. 점수 미확인 표시와 수주 상태를 자동으로 확정하지 않는 문구를 확인한다.
4. `검토 보관함 추가` 후 왼쪽 메뉴의 `검토 보관함`을 눌러 확인한다.
5. 상태 선택에서 `0건 상태`, `오류 상태`를 차례로 살펴본다.
6. 모바일에서 메뉴/목록/상세 순서를 확인한다.
7. 개선할 화면·정보·동선과 반드시 필요한 입력 필드를 정리한다.

## 사용자가 확인해야 할 핵심 질문

- 공고를 찾는 화면에서 실제 필요한 **검색 필터**와 목록 정보는 무엇인가?
- 목록 → 상세 → 기술 비교/참가요건 판단 흐름이 적합한가?
- 참가 자격을 **확인하지 않은 상태**와 기술적 관련성은 별도로 보이는가?
- 상세 화면에 공식 링크·RFP 근거·요건 우선순위를 어느 위치에 표시할 것인가?
- 사용자가 입력할 기업/기술 프로필과 분석 결과는 어느 화면이 편리한가?
- 보관함·추가 질문·알림 등 후속 기능 중 어떤 것이 실제로 필요한가?

## 승인과 후속 구현

- 검토가 끝나지 않았으면 `UI_PROPOSED / USER_FEEDBACK_PENDING`을 유지한다.
- 사용자가 수정을 요청하면 UI 시안을 먼저 고치고 화면 설계와 API 데이터 계약을 조정한다.
- 사용자의 판단이 확인되어야 `UI_APPROVED`로 전환할 수 있다. 추측하거나 자동 승인하지 않는다.
- 이 승인도 외부 API 약관, 인증/보안, 독립 코드 검수, 공개 배포 승인과는 다르다.
- 새 화면의 실제 데이터/API 기능은 퍼블리싱 검토 결과에 맞춰 작은 단위로 구현한다.

## 실제 기능·데이터 상태

데모 공고 8건은 완전한 가상 자료다. 기술 관심도·접수 상태·참가 자격·AI 추론을 실제 평가했다고 주장하지 않는다. 사용자 입력·선택은 브라우저 화면 동안만 유지하며 서버로 전송하거나 별도로 저장하지 않는다. 소스가 공개돼 있어도 공식 공고문·비공개 고객 자료·API 키는 포함하지 않는다.

## 제출·낙찰·점수 화면 설계 검증

- 회사의 실제 제출 증빙은 **공개 낙찰 정보와 구분**하여 나라장터 로그인 이력/접수증 또는 담당자 확인을 기준으로 할 계획이다.
- 공식 낙찰·개찰·계약 API는 공고/계약 단위 공개정보를 제공한다. 개별 업체의 제안서 제출 또는 기술 평가점수를 모두 제공한다는 근거는 확인되지 않았다.
- 상세 점수 UI는 기관 공개자료·개별 통보·내부 수기를 구별한다. 미확인 점수는 `0`으로 취급하지 않는다.
- 시스템 구축 시 공개 정보와 기업별 비공개 제출/제안서 데이터를 별도 접근통제 경계에 저장해야 한다.
- 조사는 [입찰 전과정 관리 조사](../research/2026-10-09-bid-lifecycle-management.md)를 따른다.
