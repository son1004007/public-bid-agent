## 화면 시안 위치

- `frontend/public/ui-review.html`: React 또는 FastAPI 설치 없이 열 수 있는 **정적 HTML/CSS/JS 퍼블리싱**.
- `frontend/public/bid-detail-review.html`: 목록에서 `전체 상세·제출·낙찰 관리`를 눌러 들어가는 **공고별 전체 상세 화면**. 독립 실행 시 `bid-detail-review.html?notice=m1`로 선택 가능.
- 기본/참가자격/RFP·평가/제출 관리/낙찰·점수/진행 이력 화면을 조작할 수 있다. 모든 수기 기록은 현재 탭 메모리 안에서만 유지한다.
- Vite를 설치·실행한 경우 `/ui-review.html`로 접근 가능하며 빌드시 `dist/ui-review.html`로 복사한다.
- 직접 다운로드해 브라우저로 열어도 사용 가능하다. **실제 나라장터·Google·모델·백엔드에 연결하지 않는다.**
- 기존 `frontend/src/App.tsx`는 초기 API 연결 샘플로 남아 있지만 **현재 우선 검토 대상은 독립 시안**이다.

## 설계 검증을 위한 화면/사용자 동선

| 화면 | 주요 행동 | 검증할 설계 판단 |
|---|---|---|
| 공고 탐색 | 공고 목록·검색어·AI/SW/DATA 필터 | 목록에서 핵심 정보가 충분히 보이는가 |
| 공고 상세 | 항목 선택 → 기술/요건/미확인 상태 표시 | 원문·법적 적격성 미확인을 명확히 이해하는가 |
| 임시 검토 보관함 | 보관함 추가 → 목록으로 이동 | 저장 동선이 필요한가, 목록과 상세의 구조가 적절한가 |
| 화면 검증 | 검토 항목을 직접 체크 | 무엇을 우선 개선할지 합의할 수 있는가 |
| 비정상 상태 | 0건/오류 선택 | 혼동하지 않고 재시도 또는 필터 변경을 이해하는가 |
| 반응형 | 휴대전화와 PC에서 메뉴/목록/상세 확인 | 작은 화면에서 상세 확인 및 탐색이 편리한가 |

## 검증 절차

1. PC/모바일에서 `ui-review.html`을 연다.
2. 검색어 `FastAPI`, AI 카테고리를 선택하여 검색 결과를 확인한다.
3. 첫 결과에서 `전체 상세·제출·낙찰 관리`를 선택한다. 기본정보, 참가자격, 제안서/평가, 제출 기록, 낙찰/점수, 진행 이력 탭을 차례로 확인한다.
4. `제출 관리`에서 제출 확인 단계와 제출 여부를 임의 값으로 입력하고, `낙찰·평가점수`에서 점수와 만점을 시험 입력한다. 실제 업체·접수증·기밀 정보는 넣지 않는다.
5. 점수 미확인 표시와 수주 상태를 자동으로 확정하지 않는 문구를 확인한다.
4. `검토 보관함 추가` 후 왼쪽 메뉴의 `검토 보관함`을 눌러 확인한다.
5. 상태 선택에서 `0건 상태`, `오류 상태`를 차례로 살펴본다.
6. 모바일에서 메뉴/목록/상세 순서를 확인한다.
7. 개선할 화면·정보·동선과 반드시 필요한 입력 필드를 정리한다.

## 사용자가 확인해야 할 핵심 질문

- 공고를 찾는 화면에서 실제 필요한 **검색 필터**와 목록 정보는 무엇인가?
- 목록 → 상세 → 기술 비교/참가요건 판단 흐름이 적합한가?
- 참가 자격을 **확인하지 않은 상태**와 기술적 관련성은 별도로 보이는가?
- 상세 화면에 공식 링크·RFP 근거·요건 우선순위를 어느 위치에 표시할 것인가?
- 사용자가 입력할 기업/기술 프로필과 분석 결과는 어느 화면이 편리한가?
- 보관함·추가 질문·알림 등 후속 기능 중 어떤 것이 실제로 필요한가?

## 승인과 후속 구현

- 검토가 끝나지 않았으면 `UI_PROPOSED / USER_FEEDBACK_PENDING`을 유지한다.
- 사용자가 수정을 요청하면 UI 시안을 먼저 고치고 화면 설계와 API 데이터 계약을 조정한다.
- 사용자의 판단이 확인되어야 `UI_APPROVED`로 전환할 수 있다. 추측하거나 자동 승인하지 않는다.
- 이 승인도 외부 API 약관, 인증/보안, 독립 코드 검수, 공개 배포 승인과는 다르다.
- 새 화면의 실제 데이터/API 기능은 퍼블리싱 검토 결과에 맞춰 작은 단위로 구현한다.

## 실제 기능·데이터 상태

데모 공고 8건은 완전한 가상 자료다. 기술 관심도·접수 상태·참가 자격·AI 추론을 실제 평가했다고 주장하지 않는다. 사용자 입력·선택은 브라우저 화면 동안만 유지하며 서버로 전송하거나 별도로 저장하지 않는다. 소스가 공개돼 있어도 공식 공고문·비공개 고객 자료·API 키는 포함하지 않는다.

## 제출·낙찰·점수 화면 설계 검증

- 회사의 실제 제출 증빙은 **공개 낙찰 정보와 구분**하여 나라장터 로그인 이력/접수증 또는 담당자 확인을 기준으로 할 계획이다. 서울지방조달청 2026년 공고문에는 `입찰 > 입찰진행 > 나의투찰내역`(가격서) 및 `입찰 > 입찰내역 > 제안서/공모안 제출내역`(제안서)을 안내한다. 공고별 제출 방법/메뉴는 원문에서 재확인한다.
- 공식 낙찰·개찰·계약 API는 공고/계약 단위 공개정보를 제공한다. 개별 업체의 제안서 제출 또는 기술 평가점수를 모두 제공한다는 근거는 확인되지 않았다.
- 상세 점수 UI는 기관 공개자료·개별 통보·내부 수기를 구별한다. 미확인 점수는 `0`으로 취급하지 않는다.
- 시스템 구축 시 공개 정보와 기업별 비공개 제출/제안서 데이터를 별도 접근통제 경계에 저장해야 한다.
- 조사는 [입찰 전과정 관리 조사](../research/2026-10-09-bid-lifecycle-management.md)를 따른다.

## 사용자 피드백 반영: 입찰 전체 라이프사이클 관리 방향 (2026-10-09)

사용자는 기존 퍼블리싱 화면 이후, 다른 업체의 실무형 입찰관리 사례를 참고해 **공고 발굴부터 수주/실패 분석까지 관리**하는 개발 방향에 동의했다. 이는 화면 정보 구조의 발전 방향에 대한 동의이며, 현재 상세 탭 전체의 사용성 승인은 아니다.

### 이어서 검토할 UI 차이

1. **Bid / No-Bid 판단**: 참여 여부만이 아니라 미참여 사유와 결정 근거 표시.
2. **제출 기록 분리**: 기술제안서와 가격입찰서는 각각 `미확인/제출 주장(수기)/접수 증빙 확인` 등의 상태로 기록. 실제 필수 제출물은 공고별 요구사항에서 결정.
3. **외부 결과 대 내부 성과**: 공고의 개찰·낙찰 결과, 우리 기업의 선정 여부, 계약 체결을 개별 정보로 표현.
4. **평가점수**: 기술/가격 점수, 각 배점과 출처를 함께 표시. 비공개나 확인 전인 점수는 `UNKNOWN`으로 보존하고 0점으로 취급하지 않음.
5. **회고**: 참여 포기 사유, 누락된 제출 항목, 미선정 원인, 다음 입찰 대응 개선사항.
6. **보안/권한**: 실제 업체 수기 기록은 향후 인증·회사별 접근통제 경계가 마련된 후 저장.

목록→상세→제출/결과→회고의 동작을 화면에서 검증한 뒤, 해당 UI에서 필요한 최소한의 API/영속 데이터 계약을 구체화한다. 실제 제출 버튼·낙찰 결과 확정·외부 사용자 정보 저장 기능은 검증 전 만들지 않는다.

## 현재 P0 실제 조작 화면 (2026-10-09)

**`frontend/public/bid-management-preview.html`**을 최우선으로 검토한다. 이 HTML을 다운로드하여 브라우저에서 바로 열거나, Vite 개발 서버의 `/bid-management-preview.html` 경로로 접근할 수 있다. 실제 API나 서버는 실행하지 않아도 된다.

### 사용자가 직접 재현할 화면 흐름

1. 메인 `진행 대시보드`에서 합성 공고 8건 목록·검색·분야/결정 필터를 확인한다.
2. `가상 진행 사례 채우기`를 눌러 Bid/No-Bid, 제출, 선정, 점수가 들어간 **가상 사례만** 확인한다.
3. 공고 목록의 `상세 관리`를 눌러 `참여 결정`에서 미참여와 사유 없이 저장하면 오류가 나는지, 사유를 입력하면 수기 기록이 반영되는지 확인한다.
4. `제출 확인`에서 **기술제안서와 가격입찰서 각각** 필요 여부·제출 상태·접수증 수기 확인·확인일을 바꿔본다. 두 서류를 서로 혼동하지 않는지 확인한다.
5. `낙찰·계약`에서 공고 전체 개찰 결과, 우리 회사 선정 여부, 실제 계약 상태가 따로 보이는지 확인한다.
6. `평가 점수`에서 점수/만점을 함께 입력하고, 미입력=미확인, 점수>만점 오류, 출처 누락 오류를 확인한다.
7. `회고`에서 미선정/포기 사유·개선사항을 기록한 후 `결과·회고` 목록으로 이동한다.
8. 모바일 화면에서 입력 필드와 탭 메뉴가 잘 보이는지 확인한다.
9. `시안 초기화` 또는 새로고침 후 입력 데이터가 남지 않는 것을 확인한다.

### 현재 구현과 비범위

- 구현: 단일 정적 HTML과 브라우저 JS 상태; 모든 기관/공고/제출/점수 예시는 합성·수기.
- 미구현: 나라장터 로그인/투찰 확인, 실제 접수증 검증, 실시간 API, 서버 저장, 역할/권한, 실사용자 점수 자동 연동.
- 실제 사용자 데이터/민감 접수번호는 데모에 입력하지 않는다.
- 사용자 승인 전: `UI_PROPOSED / USER_FEEDBACK_PENDING`, 독립 코드 최종 검수 전: `REVIEW_DEBT`.

- 필수조건 6개: 원문 근거가 없으면 미확인 유지. 조건을 '충족/미충족/해당없음'으로 바꾼 경우 출처 종류 및 근거 메모를 입력하지 않으면 저장 금지.
- 비교 평가 8개: 1~5점 또는 미확인. 점수 입력 시 출처 종류와 이유가 필수. 임의 가중치는 100 합계이며 실제 낙찰 확률이 아님.
- 경제성: 예상매출·수행원가·제안비용(만원)과 공고상 기술/가격 배점(실제 공고에서 추출 필요)을 별도로 입력해본다.
- 판단 결과: 필수조건 미충족이면 가중합을 산출해도 참여 가능으로 표시하지 않음. 미확인 조건/평점은 0으로 처리하지 않음. 모든 값이 있어도 `권고 지표`는 예시 점수이지 수주확률이 아니다.
- 참여 결정 탭으로 이동하면 입력 완료 상태와 자동 요약이 나타나고, 사용자 자신이 최종 선택한다. Codex/Claude는 실제 미연결로 표시되어야 한다.
- 사용자는 아래에서 변수 및 가중치를 검토해야 한다: [Bid/No-Bid 독립변수 명세](../design/BID_NO_BID_FACTORS.md).
