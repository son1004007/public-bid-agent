## 3. 세션 시작 절차

1. 최신 원격 main·개발 브랜치·작업 브랜치·PR·Actions SHA를 확인한다. dirty worktree/동시 작업을 확인하고 다른 변경을 덮어쓰지 않는다. 로컬에 main만 있다고 개발 브랜치 변경이 없다고 가정하지 않는다.
2. 코드 기준 SHA, 문서 기준 SHA, 현재 운영 소스(이번 작업에 필요하고 접근 권한이 있을 때만)를 구분한다. GitHub main과 사용자 PC는 별도다.
3. 작업 카드 중 **의존조건을 충족한 첫 미완료 카드 하나**를 선택한다. A01이 해결돼 있으면 반복 구현하지 말고 증거를 확인하고 다음으로 이동한다.
4. 해당 카드의 최신 상태를 `IN_PROGRESS`로 기록하고 시작 SHA·범위·검증 계획을 남긴다. 수정 전에 관련 함수/테스트를 읽는다. 중요한 설계는 사전 독립 검수를 적용한다.
5. 작은 변경→합성/경계/관련 회귀→필수 전체 CI/인수→독립 Codex 검수→지적 수정→문서 인계 순서로 진행한다. 로컬 데이터·원본 변경은 별도 보존/복구 계약을 따른다.
6. 변경 유형에 해당하는 README·설계·테스트·현재 상태·백로그를 함께 동기화한다. 제품 코드/API/UI/패키지 변경 시 루트와 local_app README 둘 다 확인한다.
7. 구현/검수/게시/운영 적용을 각각 기록한다. `DONE`은 카드의 완료 조건을 실제로 만족했을 때만 사용한다.

## 4. 막혔을 때

- 원본/회사 증빙/사람 검수가 없다: 해당 카드를 `BLOCKED_EVIDENCE`. 가짜 데이터로 실자료 통과를 만들지 않는다. 합성 테스트 성공은 따로 기록한다.
- 테스트 실패: 오류를 정상 동작처럼 바꾸지 말고 원인·영향·재현 명령을 남긴다. 기존 실패와 이번 변경의 회귀를 구분한다.
- 독립 검수 NO_GO: 지적을 증거와 함께 처리하고 재검수한다. 자기 검수를 독립 검수라고 쓰지 않는다.
- 권한/연결 부족: 무엇을 읽지/실행하지 못했는지 `BLOCKED` 또는 `NOT RUN`으로 기록한다. 현재 권한에서 가능한 비의존 작업만 수행한다.
- 이미 승인된 범위 안의 가역적 구현 선택은 불필요하게 재승인 요청하지 않는다. 실제 회사 자료 전송·공개 서비스·운영 배포·입찰 행위의 권한은 추정하지 않는다.
- 같은 차단 상태로 반복 커밋/재시도/스케줄을 만들지 않는다. 재개 조건이 바뀌었을 때 갱신한다.

## 5. 다른 AI에게 남길 인계 양식

- 시작 branch / SHA / 종료 commit 또는 PR:
- 수정 파일과 변경 이유:

- 실자료 검증 상태/표본 범위: (합성과 구분)
