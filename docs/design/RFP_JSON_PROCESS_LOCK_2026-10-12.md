# RFP 배치·대시보드 JSON 프로세스 간 동시성 보호 (2026-10-12)

## 문제와 목표

- 동일 PC에서 두 개의 로컬 서버/배치 프로세스가 각각 `dashboard.json`을 읽고 수정한 뒤 `os.replace`하면, 늦게 저장한 프로세스가 먼저 기록된 판단·첨부·추출 근거를 덮어쓸 수 있다.
- 기존 사용자 데이터와 `cases.json`·`operations.json`·`workforce.json`은 이동하거나 재작성하지 않는다.
- 동일 사용자 데이터 폴더에 대한 공고 수집·재분류·첨부 상세조회·문서추출·담당자 판단·RFP 배치의 JSON read-modify-write를 직렬화한다.

## 설계 계약

1. `local_app/json_transaction.py`의 `transaction(root)`을 공통으로 사용한다. 경로 기준 프로세스 내부 `threading.Lock`과 OS 바이트 잠금(Windows `msvcrt.locking`, POSIX `flock`)을 동시에 사용한다.
2. 같은 데이터 디렉터리의 `.dashboard-rfp.lock` 파일은 잠금 대상을 고정한다. 잠금 파일은 내용 없는 표식이며 삭제하지 않는다. 파일 삭제로 잠금을 회피하지 않는다. 기본 대기 시간은 10초로 제한한다.
3. 잠금 순서는 기존 서버/배치 `LOCK` → 공통 JSON 트랜잭션 순서이다. 파일 읽기 → 최신값 검증/병합 → 원자적 `os.replace` 저장까지 보호한다.
4. RFP 네트워크 다운로드·문서 추출 중에는 대시보드 쓰기 잠금을 보유하지 않는다. 저장 단계에서 최신 대시보드를 다시 읽고 `document_signature`을 비교하여 새로운 문서·첨부 근거가 생겼으면 낡은 다운로드 결과를 덮어쓰지 않는다.
5. `.rfp-batch-worker.lock`은 별도 수명 잠금으로 배치 작업자 하나만 활성화한다. 같은 프로세스의 서로 다른 관리자도 내부 잠금으로 중복 시작할 수 없다. 죽은 프로세스의 OS 잠금은 종료 시 해제되며, 다음 시작에서 장부 상태를 다시 읽어 재개한다.
6. 일시중지는 기존 계약대로 **진행 중인 문서 1건을 완료한 뒤** 후속 문서를 멈춘다. 다른 프로세스의 상태 변경도 다음 공고 시작 전에 확인한다. Thread.start 실패는 장부를 `PAUSED`로 돌리고 수명 잠금을 풀어 재개 가능하게 한다.
7. 재수집 시 기존 상세 API가 추가 확보한 공식 첨부 링크와 기존 RFP 추출문·의사결정 이력은 병합/보존한다. 공식 출처 보존·중복 제거를 적용한다.
8. 기존 서버 `persist`는 동일 파일 시스템의 임시 JSON → 파일 `fsync` → `os.replace`를 사용한다. 파일 형식 오류·잠금 시간 초과는 원본을 변경하지 않고 실패하도록 처리한다.

## 검증 항목

- 별도 Python 프로세스 2개의 동시 저장에서 revision, 각각의 갱신, 기존 판단·이력을 보존한다.
- 같은 프로세스의 별도 관리자와 서로 다른 프로세스의 배치 수명 잠금이 중복 실행을 차단한다.
- 잠금 대기 제한, 예외/프로세스 강제 종료 이후 잠금 해제와 재개를 확인한다.
- 다른 관리자에서 일시중지한 뒤 현재 작업 1건만 완료하고 이후 대기 상태가 남는지 확인한다.
- 작업 스레드 시작 실패 시 거짓 `RUNNING`을 남기지 않으며 배치가 재시작되는지 확인한다.
- 재수집에서 문서 본문, 공식 첨부, 기존 `final`/이력이 유지되는지 확인한다.

## 한계와 운영 게이트

- JSON 두 파일(`dashboard.json`, `rfp_batch.json`)을 DB 수준으로 한 번에 커밋하는 구조는 아니다. 문서 성공을 먼저 저장한 뒤 장부를 갱신하며, 중간 프로세스 종료 뒤 다음 시작에서 성공 상태를 대조하여 복구한다.
- `os.replace`는 프로세스 간 충돌·부분 JSON 관찰을 줄이지만, 갑작스러운 전원 차단 직후 스토리지 메타데이터까지 **영구 보장**하는 것은 아니다. 실제 PC 전원 장애 내구성은 별도 운영 검증이 필요하다.
- 동일 데이터 디렉터리를 수정하는 **외부/구형/임의 스크립트**가 잠금 계약을 따르지 않으면 충돌을 막을 수 없다. 전체 운영 서비스와 공개 배포는 별도 승인 전까지 보류한다.
- 개인 PC 실제 JSON의 일괄 변환·삭제·자동 테스트 쓰기는 허용하지 않는다.

## 2026-10-12 추가 독립 검수 및 충돌 복구 보완

- 독립 Codex가 소스·합성 테스트에서 확인한 교차 실행 결함: 구형 `/api/dashboard/enrich(-batch)`의 늦은 추출 결과가 최신 RFP 문서를 덮을 수 있음. 수정 후 저장 직전에 `document_signature`를 다시 비교하고, 신규 RFP가 있으면 해당 후보의 저장을 보류하며 `skipped_conflicts`를 반환함.
- 배치 상태가 `IN_PROGRESS`인 채 프로세스가 종료되면 다음 재개에서 `FAILED`로 격리하고, 사용자의 `retry_failed=True` 요청 전까지 자동 다운로드를 수행하지 않음. 처리 시작 전에 시도 횟수와 진행 상태를 저장해 실패 결과/ledger 저장 사이 강제 종료도 구별함.
- 배치 `RUNNING` 상태의 다른 프로세스 잠금이 유지되고 있을 때는 `PENDING` 건수가 0이어도 `start`를 거부하여 ledger를 `COMPLETE`로 잘못 바꾸지 않음.
- Windows의 별도 관리자 중복 실행 테스트, 2개 독립 프로세스 동시 revision/이력 보존, 일시중지, 잠금 시간 초과, 재수집 첨부 보존, 강제 중단 `IN_PROGRESS` 재개, 실제 루프백 HTTP의 늦은 `enrich` 저장 차단을 임시 합성 JSON으로 실행했다.
- 첫 독립 Codex 검수 SHA-256: `f0dbedb370474f1c2694f499b84f0fb11ad8c7856b0fd7ea591b9960654ee72f`. 지적 3건 중 낡은 성공 저장/실패 ledger 자동 재시도를 수정했고, 이전 세대 JSON 백업 부재는 기존 설계의 별도 복원 기능 이슈로 등록한다. `os.replace`의 원자성과 별도 백업 복구 기능을 동일한 것으로 주장하지 않는다.
- 원문 `cases.json`, `operations.json`, `workforce.json`, 실제 `dashboard.json`은 코드 테스트 및 모델 검수에 제공하지 않음. 기존 8765 서버로 수정을 적용하지 않았음.
