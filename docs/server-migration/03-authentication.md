# 03. DB 계정 인증과 최초 비밀번호 변경

[전체 목차](README.md)

## 1. 사용자 확정 요구

**SSO/OIDC/OAuth 로그인은 붙이지 않는다.** 사용자 계정은 PostgreSQL의 Django 사용자 모델을 기준으로 한다. 모든 신규/초기화 계정은 최초 인증 후 비밀번호 변경을 완료해야 업무 기능을 사용할 수 있다. 계정 없는 공개 회원가입은 기본 제공하지 않는다.

Django 기본 인증/세션/검증/해시 기능을 재사용한다. 평문·복호화 가능한 비밀번호를 DB에 저장하거나 자체 암호 알고리즘을 만들지 않는다. 프로젝트 사용자 모델은 첫 migration 전 `AUTH_USER_MODEL`로 정하고 이후 교체 비용을 피한다.

## 2. 계정 생명주기

1. 승인된 운영자가 초기 관리자 1명을 전용 관리 명령으로 생성한다. 기본 ID/공통 암호/실제 암호를 소스·시드 migration·Compose·문서에 넣지 않는다.
2. 관리자가 사용자별 계정을 발급한다. 무작위 임시 암호는 승인된 비밀 전달 경로로만 전달한다. Git·애플리케이션 로그·감사 이벤트·AI 프롬프트로 전달하지 않는다.
3. 발급/초기화 시 `must_change_password=true`, `password_changed_at=null` 또는 이전 시각 보존, `auth_epoch` 갱신으로 기존 세션을 무효화한다. 임시 암호 만료는 설정 가능한 서버 시각으로 관리한다.
4. 로그인 성공 후에도 제한 세션만 부여하고 비밀번호 변경 화면으로 이동한다.
5. 현재 임시 암호 재확인·새 암호 정책 검증·재사용 방지 확인 후 transaction 안에서 해시/변경시각/flag/epoch를 갱신한다. 관련 세션을 폐기하고 새 암호로 다시 로그인하게 한다.
6. 계정 잠금/비활성화/임시 암호 재발급/권한 변경 시 세션·작업 권한을 즉시 재검사한다. 계정 복구는 권한 있는 관리자의 재발급 절차이며 임의 메일 링크/SSO 복구를 추가하지 않는다.

업무 역할은 `관리자·담당자·검수자·조회자`를 초안으로 제시한다. 구체적 회사/부서/공고 접근 권한은 책임자 확인 전 확정하지 않는다. 관리자 역할만으로 회사 민감 원문 접근·법적 적격 승인·입찰 실행 권한을 자동 부여하지 않는다.

## 3. 서버 강제 게이트

```text
미인증 → 로그인
인증 성공 + must_change_password → 제한 세션 → 비밀번호 변경 → 세션 폐기 → 재로그인
인증 성공 + active + 변경완료 + 업무범위 권한 → 허용된 업무
계정 잠금/비활성/세션epoch 불일치 → 인증 거부 또는 세션 폐기
```

변경 전 허용 API는 세션 상태 조회, 본인 암호 변경, 로그아웃만이다. 공고 목록/원문/회사정보/내보내기/작업 제출/관리자 사이트를 포함한 **모든 업무 API와 파일 접근을 서버 middleware/permission에서 차단**한다. 관리자·superuser도 최초 변경 게이트의 예외가 아니다. 프런트 라우터만으로 통제하지 않는다. 작업 워커도 실행 직전 사용자/범위 권한을 다시 확인한다.

암호 변경 요청은 HTTP 성공 직전에 상태를 원자 변경한다. 동시 변경은 사용자 행 잠금/버전 검사로 1건만 수락하고 나머지는 충돌 처리한다. commit 전 검증/저장 실패는 transaction rollback으로 기존 해시/flag를 보존한다. commit 후 응답 유실이나 클라이언트 timeout은 변경 결과 불명으로 구분한다. 이때 이전 암호가 유지된다고 보장하지 않고, 자동 재제출/암호 재전송·재발급 없이 재로그인과 서버 세션 상태 확인으로 결과를 확인하게 한다. 인증·암호 변경 응답 원문/비밀을 일반 멱등키 결과 캐시에 보관하거나 재노출하지 않는다.

## 4. 세션·보안·API

동일 origin의 서버 세션 + `Secure`/`HttpOnly` 쿠키, 적절한 SameSite, Django CSRF 보호를 적용한다. **로그인 자체와 비밀번호 변경에도 CSRF 보호를 명시**한다. DRF 세션 인증만 설정하면 익명 로그인 POST도 자동 보호된다고 가정하지 않는다. 토큰/암호를 localStorage에 저장하지 않는다.

로그인 실패는 계정 존재를 구분하지 않는 일반 메시지, 서버 기준 횟수 제한/유한 잠금·해제 절차를 둔다. 실패율·잠금 이벤트에 암호·세션 ID·요청 body를 기록하지 않는다. HTTPS가 준비되지 않은 원격 운영은 활성화하지 않는다.

| API 초안 | 계약 |
|---|---|
| POST /api/auth/login | 계정·해시·active·만료·시도 제한 검사, 세션 회전, 변경 필요 상태 반환 |
| GET /api/auth/session | 본인 최소 정보·업무 접근 가능 여부, 비밀 미반환 |
| POST /api/auth/change-password | 제한 세션/CSRF/현재 암호/정책/잠금·버전 확인, 변경 후 모든 세션 폐기 |
| POST /api/auth/logout | 서버 세션 폐기 |
| POST /api/users | 관리자만 발급, 실제 권한 범위 검사 |
| POST /api/users/{id}/reset-password | 관리자 재발급, 변경 강제·기존 세션 폐기, 암호 감사로그 금지 |

암호 최소 길이/제한·임시 암호 수명·세션 유휴/절대 만료·잠금 임계치·재발급 전달 수단은 구현 전 보안 설정표에서 결정한다. 여기에서 미승인 숫자를 운영 정책으로 확정하지 않는다.

## 5. 필수 검증

미인증, 잘못된 암호/CSRF, 비활성/만료 계정, 직접 URL/API/파일/admin 우회, 신규 superuser 게이트, 타 사용자/타 부서 데이터, session fixation, 로그아웃/초기화 후 기존 세션, 동시 암호 변경, 약한/동일 암호, 로그인 제한, 비밀 비노출을 테스트한다. 최초 변경 flag를 false로 보내도 서버 값이 우선한다. 업무 로그인과 외부 AI 공급자 인증은 별개다.
