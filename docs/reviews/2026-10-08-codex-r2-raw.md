## 3. 발견사항

### R2-001 — MAJOR: `UNKNOWN_PRIORITY`가 SUITABLE을 막지 않는 판정 구멍

근거:

- `docs/adr/ADR-007-analysis-state-evaluation.md:8-13`
- `docs/01-requirements.md:96-104`

실패 경로:

1. 문서에서 중요한 자격 조항을 추출하지만 필수/선택 여부를 결정하지 못해 `UNKNOWN_PRIORITY`가 된다.
2. 현재 불변조건은 “필수 참가요건 중 `UNKNOWN`”만 `SUITABLE`을 막는다.
3. 우선순위 자체가 미확정인 조항은 필수요건 집합에 들어가지 않을 수 있다.
4. 잠재적 필수조건을 확인하지 않은 채 `SUITABLE`이 가능해진다.

또한 “확인된 상충이면 UNSUITABLE”이 선택사항의 상충까지 포함하는지 불명확하고, 참가자격과 기술 적합성을 분리한다고 하면서 최종 종합 판정 규칙은 정의하지 않았다.

최소 수정안:

- `UNKNOWN_PRIORITY`인 자격 관련 조항이 하나라도 있으면 `SUITABLE` 금지.
- `UNSUITABLE`은 근거가 확인된 `MANDATORY + CONFLICT`에만 적용.
- `OPTIONAL + CONFLICT`, 기술 부족, `NOT_APPLICABLE` 처리 규칙을 별도 정의.
- `eligibility_verdict`와 `technical_fit_verdict`를 별도 필드로 만들고, 종합 판정을 제공한다면 완전한 진리표를 ADR에 추가.

검증:

- `UNKNOWN_PRIORITY`, 선택조건 상충, 필수조건 상충, 필수조건 미입력, 기술 적합성만 부족한 경우의 테이블 테스트.
- 모든 조합에서 `SUITABLE` 승격 불변조건을 property-based test로 확인.

### R2-002 — MAJOR: 실행 상태·판정 결과·원문 최신성이 한 상태축에 혼재

근거:

- `docs/adr/ADR-007-analysis-state-evaluation.md:15-21`
- `docs/adr/ADR-002-procurement-data-lifecycle.md:17-18`
- `docs/02-architecture.md:81-94`

실패 경로:

- `NEEDS_REVIEW`가 사용자 판정이면서 실행 종료 상태로 사용된다.
- `STALE_SOURCE`도 실행 상태처럼 정의되지만, 성공한 분석이 나중에 정정 공고 때문에 stale이 될 수 있다.
- 완료 run은 늦은 결과로 변경하지 않는다는 불변조건과, 완료 후 `STALE_SOURCE`로 표시한다는 계약이 충돌한다.
- 구현에 따라 성공 이력이 덮어써지거나, 정정 이후에도 `SUCCEEDED`만 보여 최신 결과로 오인될 수 있다.

최소 수정안:

- 다음 세 축을 분리한다.
  - 실행: `QUEUED/RUNNING/WAITING/SUCCEEDED/FAILED/TIMED_OUT/CANCELLED`
  - 판정: `SUITABLE/NEEDS_REVIEW/UNSUITABLE`
  - 최신성: `CURRENT/STALE_SOURCE/UNKNOWN`
- 허용 전이표, terminal 상태, 취소·재개·정정 경쟁 시 DB compare-and-set/version 규칙을 명시한다.
- 정정은 과거 실행 상태를 변경하지 않고 별도 최신성 필드만 갱신한다.

검증:

- 완료 직전 취소, 취소 직후 모델 응답, 질문 중 정정, 완료 후 정정, 중복 resume를 경쟁 테스트한다.
- 과거 결과와 당시 원문 버전이 불변인지 확인한다.

### R2-003 — MAJOR: 180초 분석의 지속 실행·재시작 구조가 결정되지 않음

근거:

- `docs/02-architecture.md:14-24,92`
- `docs/adr/ADR-007-analysis-state-evaluation.md:15-29`
- `docs/03-test-plan.md:44-50,60-65`

실패 경로:

1. FastAPI 요청이나 웹 프로세스 내부 task에서 장기 분석을 시작한다.
2. 클라이언트 연결 종료, 배포 또는 프로세스 재시작이 발생한다.
3. 작업은 사라지지만 DB에는 `RUNNING`이 남거나, 복구 과정에서 중복 실행·중복 모델 사용이 발생한다.
4. 취소 토큰과 SSE 상태가 실제 작업 소유자에게 전달되지 않는다.

최소 수정안:

- 제한적 PoC는 동기식·단일 프로세스·비내구성임을 명시하고 실행 시간을 작게 제한하거나,
- 공개 구현에는 PostgreSQL 기반 job claim/lease, heartbeat, 만료 작업 회수, 상태 version/CAS, 단계별 idempotency key를 둔 별도 worker 경계를 정의한다.
- Redis/Celery 도입은 필수가 아니다.

검증:

- 단계별로 worker 강제 종료, 중복 worker claim, 배포 재시작, 취소 경쟁, lease 만료를 시험한다.
- 외부 호출이 중복되더라도 결과 중복 반영과 가능한 중복 청구를 제한하는지 확인한다.

검증:

### R2-005 — MAJOR: 공고 상태가 정정 여부와 접수 가능 상태를 혼합

- `docs/adr/ADR-002-procurement-data-lifecycle.md:12-18`

검증:

- 정정 후 OPEN, 정정 후 CLOSED, 정정 후 CANCELLED, 시간대 미확정 사례를 계약 fixture로 검증한다.

### R2-Q01 — QUESTION: 승인된 원격 LLM 경로가 생긴 뒤의 인증 수명주기

- 사용자 간 token 격리
- 병렬 호출의 사용량 예약과 실제 과금/한도 집계

제공자 프로토콜을 모르는 지금 이를 확정하지 않은 것은 결함이 아니며, `approved_remote` 구현 직전의 필수 ADR 게이트다.

### R2-Q02 — QUESTION: 비로그인 공개 기능의 남용 방지 주체

근거:

- `docs/adr/ADR-001-auth-session-ownership.md:32`
- `docs/adr/ADR-005-hosting-operations.md:20-31`
- `docs/04-operation-and-deployment.md:15-21`

공개 공고 조회를 비로그인으로 제공할 수 있지만, 요청·계정별 제한만으로는 비로그인 사용자를 어떤 기준으로 제어할지 정해지지 않았다. 공개 범위가 정해지면 IP/전역 동시성/캐시/문서 fetch 허용 여부 및 프록시 신뢰 경계를 결정해야 한다. 이는 호스팅 환경에 의존하므로 지금 수치를 못 박을 필요는 없지만 공개 배포 전에는 닫아야 한다.

## 4. 설계상 닫힌 위험과 열린 쟁점

### 설계 문서상 상당히 닫힌 위험

다음 항목은 “없다”고 지적해서는 안 된다. 다만 아직 구현 검증 전이다.

- Google OIDC 서버 code flow, state/nonce/PKCE, ID Token 검증, `issuer + sub` 식별
- opaque 서버 세션, `__Host-` 쿠키, CSRF·Origin, 세션 회전·만료
- API·질문·취소·재개·SSE의 객체별 소유권 검사와 URL bearer token 금지
- 원천 snapshot·hash·parser version 및 과거 근거 버전 보존
- 정정·취소·마감·partial/error/schema drift를 단순 0건과 구분
- 임의 URL fetch 금지, DNS/IP/redirect/proxy/TLS 검증과 격리 PDF parser
- 문서와 LLM 출력을 비신뢰 데이터로 취급하고 shell/SQL/임의 URL 도구를 금지
- `disabled/fake/approved` 모델 모드와 Google 로그인/모델 권한 분리
- 별도 종량제 API를 강제하지 않으며 미승인 원격 추론을 비활성화하는 경계
- 사용자 프로필 최소수집, 보존·삭제·백업 복원 시험 계획
- Agent 호출·토큰·시간·상태전이·질문 상한과 bounded retry/cancel 원칙
- 정확도 수치를 선험적으로 꾸미지 않고 실제 baseline 뒤 결정하는 평가 방침
- modular monolith/BFF와 단계적 기술 도입 방향

### 여전히 열린 설계 쟁점

- `UNKNOWN_PRIORITY`, 선택조건, 기술 적합성을 포함한 판정 진리표
- 실행 상태·판정·최신성의 직교 모델
- 장기 실행의 claim/lease/recovery/idempotency 구조
- passage ID 무결성과 의미상 근거 타당성의 구분
- 정정 이벤트와 공고 접수 가능 상태의 분리
- 공개 문서 내 제3자 개인정보 처리
- 계정 삭제·재가입·세션 폐기·삭제 저널
- canonical source URL과 실제 fetch URL 분리
- 승인 후 원격 모델 인증정보 수명주기
- 익명 공개 기능의 남용 방지 경계

## 5. 외부 사실 검증 보류

다음은 현재 `UNVERIFIED`이며, 지금 단계에서 설계 결함으로 단정하지 않는다.

- 제공 원문과 지정 Git 커밋의 실제 일치
- 나라장터 실제 ID·차수·정정·취소·마감·시간대·pagination 필드
- 첨부파일의 실제 호스트·redirect·파일 형식 및 URL 인증 방식
- 공공 API key 발급·rate limit·원문 저장·재배포·임베딩 조건
- Google OAuth 콘솔, 실제 redirect/origin, 현재 OIDC 세부 동작
- OpenAI SIWC/ChatGPT 플랜의 공개 원격 호스팅 자격·승인·사용 한도·비용
- 실제 모델의 인증·철회·취소·데이터 보존 정책
- PDF parser와 배포 플랫폼에서 가능한 OS 격리 방식
- 호스팅 제공자, 도메인, 백업 저장소, 비용 상한, 실제 사용자 수
- RPO/RTO, 정확도, 검색 recall, 파서 안전성 및 운영비
- 관련 법률·약관 준수 여부

이 항목들은 현재처럼 기능 게이트와 `UNKNOWN`으로 유지하되, 실제 구현·공개 출시 전에 공식 자료와 read-only probe로 확인해야 한다.

## 6. 먼저 할 5가지

1. ADR-007에 판정 진리표를 추가해 `UNKNOWN_PRIORITY`와 참가자격/기술 적합성 조합을 안전하게 닫는다.
2. `AnalysisRun` 실행 상태, 결과 판정, 원문 최신성을 서로 다른 필드와 전이표로 재설계한다.
3. ADR-002에서 정정 유형과 OPEN/CLOSED/CANCELLED 상태를 분리한다.
4. 근거 링크에 의미 검증 상태를 추가하고, 무관하지만 유효한 passage ID 공격을 출시 실패 조건에 포함한다.
5. 장기 실행의 DB lease/worker 복구 계약과 계정 삭제·공개 문서 개인정보 계약을 작성한 뒤, 실제 나라장터/API·LLM 공식 조건을 read-only로 검증한다.

결론적으로 설계는 이전 위험을 상당히 구체적으로 다뤘고 제한적 PoC로 발전시킬 기반은 있다. 다만 현재 상태에서 `READY_FOR_LIMITED_POC` 또는 공개 서비스 가능으로 승격하기에는 판정과 상태 모델의 안전 불변조건이 아직 불완전하다.
