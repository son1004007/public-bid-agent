### R4-001 — MAJOR: 근거 의미검증 상태 모델이 내부적으로 충돌한다

근거:

### R4-002 — MAJOR: 사용자별·서비스 전체 예산의 원자적 예약 계약이 부족하다

실제 실패 경로:

5. 공개 서비스가 예상한 비용/호출 상한을 보장하지 못한다.

- UTC 기준 시간창, 갱신 시점, 통화/가격표 버전, 토큰 이외 과금 단위, 미확인 사용량 처리, 환불 가능한 예약과 단조 증가 사용량을 구분한다.

검증:

- crash 직전/직후 예약 복구
- user 한도와 global 한도 중 하나라도 부족하면 외부 호출이 발생하지 않는지 확인

### R4-003 — MAJOR: 동기화 “완료”의 범위가 없어 잘못된 최신성 승격이 가능하다

- `docs/adr/ADR-002-procurement-data-lifecycle.md:18`
- `docs/adr/ADR-002-procurement-data-lifecycle.md:40-50`
- `docs/03-test-plan.md:20-26`

`last_successful_complete_sync`는 필요한 페이지/커서 전체가 성공했을 때만 갱신한다고 되어 있으나, 무엇에 대한 전체인지 식별하는 계약이 없다. API operation, 검색조건, 날짜 구간, 업무구분, pagination 세션의 범위가 빠져 있다.

실제 실패 경로:

1. “최근 7일 AI 키워드” 조회가 모든 페이지를 성공한다.
2. 구현이 이를 원천 전체의 `last_successful_complete_sync`로 기록한다.
3. 다른 업무구분이나 이전에 저장된 공고의 정정·취소가 이번 조회 범위에 없었는데도 `CURRENT`로 유지된다.
4. 실제로 취소되거나 정정된 공고가 `OPEN/CURRENT`로 표시될 수 있다.

최소 수정안:

- `SyncCoverage`를 도입하여 source operation, 필터, 기간, 업무구분, cursor/page manifest, 시작/완료 시각과 결과 상태를 식별한다.
- 특정 공고를 `CURRENT`로 만들 수 있는 조건을 “그 공고의 authoritative detail refresh 성공” 또는 “그 공고를 포함하는 증명 가능한 complete coverage”로 제한한다.
- 목록에서 사라진 사실만으로 취소를 단정하지 말고 tombstone/상세 조회 계약을 둔다.

검증:

- 서로 다른 검색조건의 동시 동기화
- 겹치는 날짜 구간, 누락 페이지, 늦게 나타난 정정본
- 목록에서는 사라졌지만 상세 상태가 불명확한 공고
- unrelated query 완료가 기존 공고의 freshness를 갱신하지 않는지 확인

### R4-004 — MAJOR: self-declared 프로필과 `SUITABLE`의 의미가 충분히 분리되지 않았다

근거:

- `docs/adr/ADR-007-analysis-state-evaluation.md:18-40`
- `docs/adr/ADR-007-analysis-state-evaluation.md:89-95`
- `docs/adr/ADR-008-profile-privacy.md:7-16`
- `docs/01-requirements.md:97-105`

문서는 사용자 답변이 검증된 자격 증거가 아니라고 정확히 밝힌다. 그러나 집계표는 “모든 필수요건 충족”이면 `SUITABLE`을 허용하며, `SATISFIED`가 검증된 사실인지 사용자의 자기신고와 일치한다는 뜻인지 구분하지 않는다.

실제 실패 경로:

1. 필수 인증 보유 여부 질문에 사용자가 `YES`를 선택한다.
2. 요구조건 원문만 의미검증되고, 사용자 답변은 자기신고 상태다.
3. 구현이 이를 `assessment=SATISFIED`로 처리한다.
4. 다른 조건이 충족되면 결과가 `SUITABLE`이 된다.
5. 면책문구가 있더라도 사용자는 자격이 확인된 것으로 오해할 수 있다.

최소 수정안:

- 프로필 사실에 `SELF_DECLARED / EXTERNALLY_VERIFIED / UNKNOWN` 같은 provenance를 별도 저장한다.
- `SATISFIED`를 “공식 자격 확인”과 “자기신고 프로필과의 일치”로 분리한다.
- 자기신고만으로도 `SUITABLE`을 허용하려면 UI 명칭을 “자기신고 프로필 기준 알려진 충돌 없음”으로 고정한다.
- 법적·행정적 필수요건은 자기신고만으로 공식 충족 상태가 되지 않도록 한다.

검증:

- 인증 보유 `YES`, 경력 범위, 기술 선택 등 자기신고 조합
- 같은 입력이 자격 축과 기술 적합성 축에서 다르게 표시되는지
- API와 UI에서 provenance가 누락되지 않는지
- 자기신고가 공식 검증 상태로 승격되지 않는지

### R4-005 — MAJOR: 인증된 응답과 edge/shared cache의 격리 계약이 없다

근거:

- `docs/02-architecture.md:9-31`
- `docs/adr/ADR-001-auth-session-ownership.md:20-40`
- `docs/adr/ADR-005-hosting-operations.md:7-18`

백엔드 객체권한은 상세하지만, HTTPS reverse proxy/CDN이 사용자별 GET 응답, 분석 결과, 근거, export 또는 SSE를 공유 캐시하지 못하게 하는 응답 계약은 없다.

실제 실패 경로:

1. 사용자 A가 `/api/analysis-runs/{run_id}`를 조회한다.
2. 잘못 설정된 reverse proxy가 cookie-authenticated 응답을 URL 기준으로 캐시한다.
3. URL을 알게 된 사용자 B의 요청이 backend에 도달하지 않고 캐시에서 응답된다.
4. 애플리케이션의 ownership 검사는 정확해도 사용자 A의 결과가 유출된다.

최소 수정안:

- 라우트를 `public-cacheable`, `authenticated-private`, `streaming`, `download/export`로 분류한다.
- 사용자별 응답은 `Cache-Control: private, no-store`를 기본으로 하고 edge cache를 우회한다.
- SSE는 buffering/cache를 비활성화한다.
- export URL과 결과물도 별도의 짧은 TTL·일회용 권한 계약을 둔다.
- 공개 공고 캐시와 사용자 분석 캐시를 설정 수준에서 분리한다.

검증:

- 실제 선택한 reverse proxy/CDN을 통과하는 두 사용자 E2E
- cache hit/miss 헤더 및 로그 확인
- 로그아웃·탈퇴 후 브라우저 back/edge cache 재조회
- SSE buffering과 재연결 중 다른 run 혼입 여부 확인

### R4-006 — MAJOR: 계정 삭제와 이미 진행 중인 외부 모델 요청의 의미가 빠져 있다

- `docs/adr/ADR-008-profile-privacy.md:20-28`
- `docs/adr/ADR-008-profile-privacy.md:34-42`

삭제 시작 후 신규 작업과 결과 저장을 차단하는 계약은 좋다. 하지만 삭제 직전에 이미 외부 모델로 전송된 요청을 취소할 수 없는 경우의 처리·고지·완료 조건이 없다.

실제 실패 경로:

1. worker가 프로필의 허용 필드를 외부 모델에 전송한다.
2. 직후 사용자가 계정을 삭제한다.
3. 로컬 세션과 결과 저장은 차단되지만 provider는 계속 처리하거나 일정 기간 입력을 보존한다.
4. 서비스가 즉시 완전 삭제됐다고 표시하면 실제 외부 처리 상태와 불일치한다.

최소 수정안:

- `DELETING` 이후 신규 전송 금지와 이미 전송된 요청을 명시적으로 구분한다.
- provider 취소 API가 있으면 호출하고, 없으면 결과 폐기 및 provider 보존 정책에 따른 잔존 가능성을 고지한다.
- 삭제 완료 상태가 로컬 삭제 완료인지, 외부 provider 처리/보존 종료까지 포함하는지 정의한다.
- 외부 요청 ID는 개인정보를 포함하지 않는 최소 추적값으로 삭제 작업과 연결한다.

검증:

- 외부 요청 직전·직후·응답 직전의 삭제 경쟁
- provider cancel 지원/미지원/실패
- 늦은 응답이 DB·로그·SSE에 저장되지 않는지
- 삭제 상태와 사용자 고지가 실제 provider 계약과 일치하는지

한편으로 terminal 이벤트 전달 후 stream 종료라고 하고, 다른 한편으로 run 취소 상태가 되면 다음 이벤트와 heartbeat를 보내지 않고 즉시 종료하도록 한다.

실제 실패 경로:

- 사용자가 취소 POST를 성공시켰지만 열린 UI stream은 `CANCELLED` 이벤트 없이 끊어진다.
- UI가 이를 네트워크 오류로 표시하거나 재연결을 반복한다.

최소 수정안:

- 계정/세션/소유권 철회와 run 취소를 분리한다.
- 권한이 여전히 유효하면 최소 `CANCELLED` terminal 이벤트 1개를 보내고 종료할지, 아니면 terminal 전달을 보장하지 않고 polling을 권위 상태로 삼을지 하나로 확정한다.

검증:

- 취소, 로그아웃, 탈퇴, 세션 만료 각각의 stream 결과
- terminal 이벤트 중복과 재연결 처리

### R4-008 — MINOR: Google OIDC 최소 scope가 명시되지 않았다

근거:

- `docs/adr/ADR-001-auth-session-ownership.md:10-18`
- `docs/adr/ADR-008-profile-privacy.md:9-16`

서비스 식별에는 `issuer + sub`만 필수라고 하면서 실제 요청 scope와 불필요한 email/name claim의 폐기 정책이 없다.

실제 실패 경로:

- 구현자가 관행적으로 `openid email profile`을 요청하고 이메일과 이름을 저장한다.
- 설계의 최소수집 원칙보다 많은 개인정보를 동의·필요성 정의 없이 수집하게 된다.

최소 수정안:

- 초기 scope를 명시하고 이메일/프로필 scope 추가 조건을 별도 결정으로 둔다.
- 불필요한 claim은 저장·로그하지 않는다고 명시한다.

검증:

- 실제 동의 화면과 토큰 claim 확인
- DB·세션·로그에 email/name이 남지 않는지 확인

### R4-Q01 — QUESTION: 공개 출시 평가 게이트의 최종 형태

근거:

- `docs/03-test-plan.md:72-81`
- `docs/adr/ADR-003-evidence-retrieval.md:26-30`

측정 전 임의 수치를 약속하지 않는 결정은 타당하다. 다만 공개 출시 전에는 표본 크기, 중요 오류 slice, 회귀 허용범위와 승인 주체가 실제 baseline에 근거해 확정되어야 한다. 지금 수치가 없는 것은 결함이 아니지만, “결과 1건 이상”만으로 출시해서는 안 된다.

검증 방법은 버전 고정된 holdout 자료, 필수요건 누락/잘못된 긍정 판정 별도 집계, 평가자료와 prompt 개발자료 분리, 독립 최종 검토다.

### R4-Q02 — QUESTION: 원본 PDF의 저장·격리·제공 정책

근거:

- `docs/adr/ADR-006-document-ingestion-security.md:14-18`
- `docs/adr/ADR-006-document-ingestion-security.md:29-36`
- `docs/adr/ADR-003-evidence-retrieval.md:18-23`

원본 보존 여부를 권리 조건에 따르도록 안전하게 보류했지만, 저장을 허용하는 출처가 생길 경우 원본 PDF를 같은 origin에서 직접 제공할지 여부는 확정해야 한다.

최소 안전 원칙은 저장 원본을 공개 정적 파일로 제공하지 않고, 격리 저장·명시적 다운로드 정책·안전한 content disposition을 적용하거나 공식 canonical 링크만 제공하는 것이다.

## 4. 현재 원문에서 설계상 닫힌 위험

다음 항목은 이미 문서에 실질적인 통제가 있으므로 “누락”으로 보지 않았다.

- Google 로그인과 ChatGPT/Codex 모델 권한의 분리
- 서버 OIDC code flow, state/nonce/PKCE, ID Token 검증, opaque 세션
- CSRF/Origin, 서버 파생 actor, 리소스별 ownership
- 열린 SSE 연결의 지속적 세션·계정·소유권 재검사
- 공고 revision, 접수상태, 마감, source freshness의 축 분리
- 정정·취소 이후 과거 분석 snapshot 불변 유지
- partial pagination, schema drift, rate limit과 실제 0건 구분
- 임의 URL fetch 금지와 DNS/IP/redirect/proxy/TLS 경계
- 격리 PDF 파서, byte/page/CPU/memory/time 제한
- 악성 문서를 지시가 아닌 데이터로 처리하는 원칙
- parser 성공과 추출 완전성 분리
- passage 존재 검증과 의미상 근거 검증의 개념적 분리
- 필수조건 UNKNOWN 및 불완전 추출 시 `SUITABLE` 금지
- terminal run 상태, lease/CAS, 취소 후 늦은 결과 저장 방지
- 후속 질문을 비민감 enum으로 제한하고 자유 입력·업로드 금지
- React text-node 렌더링, 위험 URL/HTML/Markdown 비활성
- 개인정보 최소수집, 계정 삭제, 새 내부 ID 재가입, 삭제 저널
- 모델 이용조건 미확정 시 `disabled`로 유지하는 정직한 fallback
- fake provider를 실제 AI로 표시하지 않는 요구사항

여전히 열린 설계 쟁점은 R4-001부터 R4-006까지다. R4-007과 R4-008은 공개 구현 중 계약 혼선을 방지하기 위해 함께 정리하는 것이 좋다.

## 5. 외부 사실 검증 보류 상태

다음은 `UNVERIFIED`이지만, 현재 문서가 fail-closed 또는 기능 비활성으로 처리하므로 그 자체를 설계 결함으로 분류하지 않았다.

- 나라장터 natural key, revision/정정/취소 필드, 시간대, 첨부 식별자
- 실제 API pagination, 부분 실패, 호출 제한, 인증키 및 이용조건
- 공고·PDF 원문 저장·재배포·임베딩 허용 범위
- 실제 공식 PDF 제공 호스트, redirect, 파일 크기와 형식 분포
- Google OAuth 콘솔, redirect/origin, 운영 도메인, 키 회전
- Google 최근 재인증과 `auth_time`을 이용한 고위험 작업 확인 가능성
- 공개 원격 호스팅 앱에서 SIWC/ChatGPT 플랜 연동 자격과 승인
- 승인 provider의 토큰 저장·철회·갱신·비용·사용량 보고 계약
- 모델 입력/출력 보존, 데이터 처리 지역 및 사용자 동의 조건
- 선택할 호스팅·reverse proxy·DB·backup 환경
- RPO/RTO, rate limit, parser 상한, worker 처리량의 실제 측정값
- AI/SW 분류, 추출, 검색, 판정 품질의 실제 baseline과 출시 임계치

이 항목들은 공개 서비스 출시 전에 실제 공식 자료와 E2E 증거로 닫아야 하지만, 제한 PoC에서는 명확히 제외하거나 합성 fixture로 대체할 수 있다.

## 6. 먼저 할 5가지

1. R4-001과 R4-004를 먼저 수정해 근거 검증 상태와 자기신고 기반 판정의 단일 진리표를 확정한다.
2. 공공 API 어댑터 구현 전에 R4-003의 `SyncCoverage`와 공고별 freshness 승격 조건을 문서화한다.
3. R4-002의 run/user/provider/global 원자적 예산 원장을 설계하고 취소·timeout·중복 worker 회귀표를 만든다.
4. R4-005와 R4-006을 반영해 private response/cache, export, SSE, 계정 삭제와 외부 in-flight 요청 계약을 확정한다.
5. 그 후 제한 PoC를 하나의 API 계약 fixture와 하나의 PDF로 실행하되, LLM·공개 배포·법적 적합성 주장은 비활성화하고 실제 API/Google/OpenAI 검증은 별도 게이트로 진행한다.
