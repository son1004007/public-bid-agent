**판단 근거:**
아키텍처 모듈 분리와 과도한 인프라 도입 억제(Kubernetes/MSA 배제), 외부 입력값(Untrusted Data)에 대한 방어적 태도는 훌륭합니다. 하지만 프로젝트의 핵심 축인 "사용자별 LLM 무료/구독 연결 방안"이 기술적·정책적으로 불확실성이 크며(BLOCKER), 인증과 외부 첨부파일 파싱 등에서 구체적인 보안 설계가 누락되어 있습니다. 해당 부분의 위험을 해소하는 ADR 확정 및 설계 보완 후 구현에 착수해야 합니다.

## 🔍 식별된 Finding 목록

### [F-01] 제3자 LLM(Codex/ChatGPT) 사용자별 인증 및 비용 구조의 기술적 타당성 부족
- **원시 심각도:** **BLOCKER**
- **원문 파일/행:** `docs/00-project-context.md:L0038-L0039`, `docs/01-requirements.md:L0120`
- **문제점:** "별도 API 사용료를 전제로 하지 않고", "사용자별 ChatGPT/Codex 연결 희망"을 요구하고 있으나, 서버 기반 애플리케이션에서 사용자의 개별 LLM 구독을 활용하려면 사용자의 개인 API Key를 서버가 입력받아야 합니다. 이는 OpenAI 등 제공자의 약관 위반 소지가 높으며 중대한 보안 위험(Secret 노출)입니다. 공식적인 OAuth/OIDC 기반 위임 프로토콜이 지원되지 않는 한 이 방식은 불가합니다.
- **현재 영향:** MVP 목표 자체의 달성 불가 및 보안 정책(Secret 수집 금지) 위반 위험.
- **구체적 수정안:** 사용자 개별 API Key 수집을 금지하고, 개발자가 제공하는 단일 서버 API Key를 사용하되 엄격한 Rate Limit을 적용하는 방식(비용 통제)으로 ADR-004를 확정해야 합니다. 또는 완전한 로컬 모델(Ollama 등)을 사용하는 것으로 변경해야 합니다.
- **수정 검증 방법:** 확정된 `ADR-004` 문서를 통해 API Key 수집 방지 및 비용/호출 제한 정책이 명시되었는지 검토.

### [F-02] OAuth/OIDC 및 애플리케이션 세션 보안 설계 누락
- **원시 심각도:** **MAJOR**
- **원문 파일/행:** `docs/01-requirements.md:L0021-L0028`, `docs/02-architecture.md:L0137-L0140`
- **문제점:** Google OIDC/OAuth 로그인에 대한 요구사항은 있으나, CSRF 방어를 위한 `state`, Replay 공격 방어를 위한 `nonce`, 모바일/SPA 환경을 위한 `PKCE` 사용에 대한 명시가 없습니다. 발급된 세션 쿠키의 `HttpOnly`, `Secure`, `SameSite` 속성 정의도 누락되었습니다.
- **현재 영향:** CSRF, 세션 하이재킹 등 웹 애플리케이션의 기본 보안 취약점 발생 가능.
- **구체적 수정안:** `ADR-001` 또는 보안 요구사항(REQ-SEC)에 OIDC 인증 시 `state`, `nonce`, `PKCE` 검증 필수화 및 세션 쿠키 발급 시 `HttpOnly; Secure; SameSite=Lax(또는 Strict)` 적용을 명시.
- **수정 검증 방법:** 인증 관련 아키텍처 문서 및 단위 테스트 계획(`docs/03-test-plan.md`)에 해당 보안 검증 항목이 추가되었는지 확인.

### [F-03] 문서 수집 시 파서(Parser) 격리(Sandbox) 및 ZIP Bomb 방어 부재
- **원시 심각도:** **MAJOR**
- **원문 파일/행:** `docs/02-architecture.md:L0145-L0163`
- **문제점:** 허용 Host, 크기 제한, SSRF 방어는 훌륭하게 명시되었으나, 복잡한 문서(PDF, HWP)나 압축 파일 파싱 과정에 대한 프로세스 수준의 격리 방안이 없습니다. 
- **현재 영향:** 악성 문서를 통한 메모리 고갈(OOM, ZIP Bomb)이나 파서 취약점을 통한 RCE(원격 코드 실행) 공격에 백엔드 서버가 직접 노출됩니다.
- **구체적 수정안:** 문서 수집 정책에 "압축 파일 해제 비율(Compression Ratio) 제한 및 최대 해제 크기 제한", "복잡한 문서 파싱 시 제한된 권한/메모리의 별도 프로세스(Sandbox) 사용"을 추가.
- **수정 검증 방법:** 문서 파싱 모듈 설계도에 파서 격리 모델이 반영되었는지 및 `docs/03-test-plan.md`에 ZIP Bomb 방어 테스트가 명시되었는지 확인.

### [F-04] 공공 입찰 API의 데이터 생명주기(취소/정정) 처리 누락
- **원시 심각도:** **MAJOR**
- **원문 파일/행:** `docs/01-requirements.md:L0039-L0046`
- **문제점:** API를 통한 입찰 공고 수집 시 '중복 제거'는 명시되어 있으나, 조달청 공고의 특성인 **정정 공고** 및 **취소 공고** 발생 시 기존에 분석된 결과(DB)를 어떻게 무효화하고 재분석할지에 대한 데이터 상태 관리(Lifecycle) 정책이 없습니다.
- **현재 영향:** 공고 조건이 변경되거나 취소되었음에도 사용자가 이전 분석 결과를 보고 '적합'으로 오판하여 금전적/시간적 손실 발생.
- **구체적 수정안:** 공고 수집 및 표준 데이터 모델에 '공고 차수' 및 '공고 상태(정상, 정정, 취소 등)' 필드를 추가하고, 상태 변경 시 이전 AI 분석 결과를 무효화(`NEEDS_REVIEW` 또는 `CANCELLED`)하는 규칙을 도메인 로직에 반영.
- **수정 검증 방법:** 입찰 공고 표준 데이터 모델 및 관련 Unit Test에 공고 상태 변경 시나리오가 추가되었는지 확인.

### [F-05] SSE(Server-Sent Events) 인증 토큰 전달 방식 불명확
- **원시 심각도:** **MINOR**
- **원문 파일/행:** `docs/01-requirements.md:L0096-L0104`, `docs/02-architecture.md:L0069`
- **문제점:** SSE 사용자 격리는 요구사항에 있으나, 일반적인 브라우저 `EventSource`는 HTTP Authorization 헤더(Bearer 토큰)를 지원하지 않습니다. 이에 대한 인증 토큰 전달(URL Query 등)에 따른 토큰 유출 위험 방지 설계가 누락되었습니다.
- **현재 영향:** URL 로그에 세션 토큰이 남거나, SSE 엔드포인트에 대한 미인증 접근이 발생할 수 있음.
- **구체적 수정안:** SSE 연결을 위해 수명이 아주 짧은(예: 30초) 1회용 Ticket을 REST API로 선발급 받아 EventSource URL에 포함시키는 방식 설계 추가.
- **수정 검증 방법:** 아키텍처 문서 및 API 명세에 SSE Ticket 발급 및 소모 과정이 명시되었는지 확인.

## 🏗️ 재설계 방향 (작게 시작하는 MVP 우선) 및 선행 작업

포트폴리오의 완성도를 위해 `React + FastAPI + LangGraph + pgVector`를 모두 한 번에 구축하는 것은 지양해야 합니다. AI의 판별 정확도와 공공 API 연동이 이 프로젝트의 핵심 가치입니다.

**최우선 재설계 방향:** 
화면(Frontend)이나 데이터베이스를 구축하기 전에, 조달청 API와 단일 LLM 스크립트가 실제로 유의미한 결과를 내는지 검증하는 **Core Proof of Concept (PoC)**부터 시작해야 합니다.

**선행 작업 상위 5개:**
1. **[PoC] 나라장터 API 실제 데이터 확보:** 조달청 API를 호출하여 실제 '공고문(JSON/XML)'과 '첨부파일(RFP/규격서)'을 다운로드하고, 파일의 형식(PDF/HWP 비율)과 데이터 구조(공고 차수 등)를 확인하는 스크립트 작성.
2. **[설계] ADR-004 확정 (LLM 인증/비용):** 사용자 API Key 입력 방안을 폐기하고, 서버 보유 Key를 사용하되 IP/계정 기반 엄격한 Rate Limit(예: 일 5회 분석)을 적용하는 방향으로 의사결정 기록.
3. **[PoC] Prompt & Extraction 검증:** 확보한 실제 RFP 텍스트 샘플과 하드코딩된 '기업 프로필(JSON)'을 기반으로, LLM(Codex/Gemini 등)이 참가 요건을 정확히 추출하고 적합성을 판정하는지 평가하는 단일 Python 스크립트 실행 (LangGraph 없이 LangChain/단일 API 호출만 사용).
4. **[설계] ADR-001 및 ADR-002 구체화:** OIDC(PKCE, state, 세션 쿠키) 보안 요건과 외부 문서 샌드박스 파싱 전략을 구체적인 기술 스택과 함께 확정.
5. **[설계] 공고 생명주기 데이터 모델링:** DB 설계 시 '공고(Notice)'와 '분석(Analysis)' 엔티티 간의 관계를 재정의하여 취소/정정 공고 발생 시의 무효화 트리거 규칙 설계.

## ⚠️ 미검증 영역 (현재 리뷰에서 확인되지 않은 사항)
- **외부 API 신뢰성:** 나라장터 공공데이터포털 API의 실제 응답 속도(Latency), Rate Limit, 첨부파일 다운로드 링크의 유효 기간 및 실제 접근 가능성 (종종 캡챠/세션이 필요하거나 다운로드 서버가 별도로 분리되어 있을 수 있음).
- **RFP 문서 형식 비율:** 첨부된 제안요청서(RFP) 중 기계 독해가 어려운 스캔본 PDF나 HWP 형식의 실제 비중.
- **LLM 추론 품질(Quality):** RAG(pgVector) 적용 시 긴 공고문에서 정확한 참가 자격 조건을 누락 없이(High Recall) 추출해 낼 수 있는지에 대한 실제 Hit Rate 및 할루시네이션(환각) 비율.
- **실제 비용 구조:** 하나의 공고를 분석할 때 소비되는 Token 수와 소요 시간(API 응답 대기 시간).
