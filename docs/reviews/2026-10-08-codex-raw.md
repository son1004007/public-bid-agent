## 핵심 종합 판단: HOLD

방향성은 양호하다. 특히 미구현 상태 표시, 원문과 AI 해석의 분리, 서버 권한 판정, deterministic rule 우선, Codex 지원 여부에 대한 유보, modular monolith 선택은 적절하다.

그러나 현재 문서는 구현 착수 기준으로 보기에는 핵심 계약이 열려 있다. 인증·세션, 공고 식별과 개정, 문서 수집 격리, claim-evidence 데이터 모델, 사용자별 실행/SSE 권한, LLM 실행 한도, 개인정보 수명주기와 운영 복구가 아직 체크리스트 수준이다. `READY WITH ASSUMPTIONS` 표시는 이 상태와 맞지 않는다.

확인된 즉시 악용 가능한 구현물이 없으므로 **BLOCKER는 부여하지 않는다**. 다만 아래 MAJOR를 닫기 전에 공개 서비스나 전체 AI 파이프라인 구현으로 진행하는 것은 부적절하다.

## Findings

### DSR-001 — 구현 준비 상태 표시가 미결정 설계와 충돌

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:5-6` — 설계 기준 `READY WITH ASSUMPTIONS`
  - `docs/02-architecture.md:176-182` — 인증, 수집, embedding, Codex, hosting ADR 전부 미결정
  - `CURRENT_STATE.md:20-26` — 실제 API, OAuth, LLM 인증, 비용·배포 대상 미확인
  - `TASKS.md:11-13` — 독립 리뷰와 주요 지적 반영, 실제 API 검증 미완료
- 실패 경로: 개발자가 현재 상태를 구현 승인으로 해석하면 인증 방식과 데이터 키를 확정하지 않은 채 DB/API 계약을 작성한다. 뒤늦은 ADR에서 세션·식별자가 바뀌면 migration과 권한 로직을 재작성해야 한다.
- 영향: 재작업뿐 아니라 tenant scope나 provenance가 빠진 초기 스키마가 굳을 수 있다.
- 수정안:
  - 상태를 `HOLD / DESIGN REVIEW REQUIRED` 또는 `NOT IMPLEMENTATION READY`로 통일한다.
  - 구현을 허용할 수 있는 범위를 “비인증 fixture 기반 vertical slice”처럼 명시한다.
  - ADR별 선행조건과 승인 기준을 표로 연결한다.
- 검증:
  - `CURRENT_STATE`, `TASKS`, 요구사항 상태가 같은 gate를 가리키는지 확인한다.
  - 미결정 ADR 없이 구현 가능한 작업과 금지된 작업을 리뷰어가 구분할 수 있어야 한다.

### DSR-002 — OIDC와 애플리케이션 세션 보안 계약이 부족함

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:21-28` — backend 신원 검증과 세션만 명시
  - `docs/02-architecture.md:135-143` — 상세 방식은 ADR로 유보
  - `docs/04-operation-and-deployment.md:20-21` — redirect/origin과 HTTPS gate만 존재
  - `docs/03-test-plan.md:20-27` — state/nonce/CSRF/session fixation 검증 없음
- 실패 경로: 공격자가 로그인 callback을 교차 세션에 주입하거나, 상태 변경 API에 cross-site 요청을 보내거나, 탈취·고정된 세션을 재사용한다. ID Token의 issuer/audience/nonce/time claim을 불완전하게 검사하는 구현도 현재 검수 기준을 통과할 수 있다.
- 영향: 로그인 CSRF, 계정 혼동, 세션 탈취·고정, 만료 후 접근 가능성이 설계상 배제되지 않는다.
- 수정안:
  - ADR-001에서 flow와 client 유형을 먼저 고정한다.
  - authorization code flow 기준으로 redirect URI exact match, `state`, `nonce`, PKCE 적용 여부와 근거를 명시한다.
  - ID Token의 서명, `iss`, `aud`/필요 시 `azp`, `exp`, `iat`, `nonce` 검증 및 key rotation 실패 정책을 명시한다.
  - 세션 cookie의 `HttpOnly`, `Secure`, `SameSite`, path/domain, TTL·idle timeout·rotation·logout invalidation을 정한다.
  - cookie 인증이면 상태 변경 API와 SSE 연결 방식에 맞는 CSRF 방어 및 CORS 정책을 정의한다.
- 검증:
  - state/nonce 불일치, 잘못된 issuer/audience, 만료 토큰, callback 재사용, session fixation, cross-site POST, logout 후 재사용 테스트를 추가한다.

### DSR-003 — 객체 권한과 SSE 격리가 원칙만 있고 리소스 계약으로 정의되지 않음

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:35,98-103,126`
  - `docs/02-architecture.md:63-70,139`
  - `docs/03-test-plan.md:22-25,87-90`
- 실패 경로: 인증 사용자 A가 URL의 `analysis_id` 또는 `run_id`를 B의 값으로 바꿔 조회·취소·재연결한다. 구현이 단순히 “로그인 여부”와 실행 ID만 검사하면 B의 이벤트 또는 결과가 노출된다.
- 영향: 기업 프로필과 분석 결과의 사용자 간 유출, 타 사용자 작업 취소, 실행 상태 추측.
- 수정안:
  - `Profile`, `AnalysisRun`, `Question`, `EvidenceSet`, SSE subscription의 소유 관계와 조회·수정·취소 권한 행렬을 작성한다.
  - 모든 명령과 조회가 `(server_actor_id, resource_id)`로 수행되도록 application contract를 정한다.
  - SSE는 사용자가 제공한 channel/user ID를 신뢰하지 않고 run ownership을 연결 시점과 재연결 시점 모두 검사한다.
  - 예측 불가능한 ID는 보조 방어일 뿐 ownership 검사를 대체하지 않는다고 명시한다.
- 검증:
  - 두 사용자 fixture로 CRUD, 결과 조회, SSE 연결/재연결, 질문 응답, 취소를 교차 수행해 일관되게 거부되는지 확인한다.

### DSR-004 — 나라장터 데이터의 정체성·개정·마감 시각 계약이 없음

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:39-46` — source ID, 장애/0건, 결정적 중복 처리만 요구
  - `docs/02-architecture.md:91-99` — 날짜·source ID·중복은 deterministic 처리
  - `docs/00-project-context.md:46-61` — 실제 API 특성은 개괄만 기재
  - `CURRENT_STATE.md:23` — 실제 작업/필드/첨부 방식 미검증
- 실패 경로: 같은 사업의 정정 공고나 차수별 공고를 중복으로 합치거나, 반대로 동일 공고를 별도 항목으로 저장한다. 마감 시각의 timezone 또는 포함 경계를 잘못 해석해 이미 마감된 공고를 “지원 가능”으로 표시한다.
- 영향: 핵심 사용자 질문인 “현재 검토/지원 가능한가”에 잘못 답하고, 오래된 문서를 근거로 분석할 수 있다.
- 수정안:
  - 실제 API 표본을 확인한 뒤 원천별 natural key, revision/version, cancel/correction 관계, 첨부 ID, 최종 관찰 시각을 정의한다.
  - raw snapshot과 normalized record를 분리하고 parser/schema version을 저장한다.
  - 원천 시각 문자열, 해석 timezone, 수집 시각을 별도 보존한다.
  - 0건, partial page, rate limit, schema drift, stale cache, 취소·정정 공고 상태를 명시적으로 모델링한다.
- 검증:
  - 실제로 관찰한 익명화 fixture로 중복, 정정, 취소, 페이지 중복, 마감 경계, malformed date, upstream partial failure contract test를 작성한다.

### DSR-005 — 첨부파일 수집 보안이 정책 목록에 머물고 격리·압축 해제 한도가 빠짐

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:57-64`
  - `docs/02-architecture.md:145-162`
  - `docs/03-test-plan.md:42-51`
- 실패 경로: 허용 host가 내부 IP로 해석되거나 redirect가 다른 목적지로 이동한다. 작은 ZIP이 대용량으로 팽창하거나 중첩 archive가 CPU·디스크를 소진한다. PDF/HWP 계열 parser 취약점 또는 무한 처리로 backend worker가 중단된다.
- 영향: SSRF, 자원 고갈, parser compromise, 서비스 거부, 악성 산출물 저장 가능성.
- 수정안:
  - URL별 scheme/port/host 허용 규칙과 DNS 해석 후 private/link-local/loopback 차단, redirect마다 재검증, redirect 수 제한을 정한다.
  - compressed size, uncompressed total, entry count, nesting depth, page count, 처리 시간·메모리·임시 디스크 상한을 둔다.
  - `Content-Type`, magic bytes, 확장자 불일치 정책을 정의한다.
  - parser를 최소권한 별도 process/container에서 network off, read-only 입력, 임시 저장소 quota, timeout으로 실행한다.
  - 초기 MVP 지원 형식을 PDF 1종 등으로 좁히고 ZIP/HWP는 실제 필요성 검증 후 추가한다.
- 검증:
  - DNS/redirect 우회, MIME 위장, oversize stream, ZIP bomb fixture, parser hang/crash, 중첩 archive를 테스트하고 backend가 제한된 오류로 복구하는지 확인한다.

### DSR-006 — 근거 모델이 “metadata 유지” 수준이며 결론에서 원문까지의 재현성을 보장하지 못함

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:66-73,82-85,127`
  - `docs/02-architecture.md:108-121`
  - `docs/05-coding-standards.md:60-69,207-215`
- 실패 경로: 원문이 정정되거나 parser/chunker가 변경된 뒤 기존 분석 링크가 현재 문서의 다른 구간을 가리킨다. LLM이 존재하지 않는 page/section을 생성해도 단순 문자열 citation으로 저장된다.
- 영향: 공식 원문 근거를 제공한다는 핵심 가치가 약화되고 결과를 재현하거나 감사할 수 없다.
- 수정안:
  - `SourceDocumentVersion`, `ParsedArtifact`, `Passage`, `ExtractedRequirement`, `Claim`, `EvidenceLink`를 최소 데이터 계약으로 정의한다.
  - 원문 hash/version, parser·chunker version, 안정적인 passage ID, page 또는 character offsets, source URL, fetch time을 저장한다.
  - claim마다 `supports`/`contradicts`/`insufficient` 관계와 검증된 passage ID만 연결한다.
  - LLM이 임의 citation을 만들지 못하도록 반환 ID를 허용 목록과 대조한다.
  - 원문 미보관 시에도 해당 hash와 위치를 재현할 수 있는 정책을 정한다.
- 검증:
  - 문서 개정, parser 재실행, chunk 순서 변경, 허위 passage ID, evidence 없음 사례에서 과거 결과가 변조되지 않고 `NEEDS_REVIEW`로 처리되는지 확인한다.

### DSR-007 — Agent/tool 실행 권한, 중단·취소 및 자원 예산이 정의되지 않음

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:87-94` — bounded retry/timeout만 요구
  - `docs/02-architecture.md:73-106,123-133`
  - `docs/03-test-plan.md:53-62`
  - `docs/04-operation-and-deployment.md:25,37-43`
- 실패 경로: prompt injection 문서가 반복 검색·재수집을 유도하거나 workflow가 질문/재개 루프에 갇힌다. 사용자가 연결을 끊거나 취소해도 backend 실행과 LLM 호출이 계속된다.
- 영향: 비용·CPU·외부 API quota 소진, 낮은 응답성, 실행 상태 불일치.
- 수정안:
  - run별 최대 node 전이, tool call 수, 문서 수/바이트, model tokens, wall-clock time, retry budget을 정의한다.
  - tool은 typed allowlist와 고정된 capability만 제공하고 arbitrary URL, shell, DB query 기능을 주지 않는다.
  - 질문 대기 TTL, 취소 상태, 취소 전파, terminal state 및 중복 resume idempotency를 정의한다.
  - 외부 문서와 사용자 텍스트는 system/tool policy와 분리된 데이터 필드로 전달한다.
- 검증:
  - 무한 follow-up, 반복 tool 요청, 취소 중 호출, 중복 resume, timeout 직후 late result, prompt injection fixture에서 예산 초과와 상태 전이가 결정적으로 종료되는지 확인한다.

- 심각도: **MAJOR**
- 근거:
  - `docs/00-project-context.md:31-40`

  - `docs/02-architecture.md:39-41,108-121,141-143`

- 실패 경로: Codex/ChatGPT 구독 인증을 서버의 제3자 사용자용 inference credential처럼 사용할 수 있다고 가정하고 설계를 진행한다. 반대로 공식 지원이 없을 경우 fake provider 외 실제 데모 경로가 없어 핵심 분석을 시연하지 못한다.
- 영향: 비용 요구를 지키면서 사용자 가치를 제공할 수 있는지 불명확하고, 인증·약관 위반 또는 공개 데모 중단 위험이 있다.
- 수정안:
  - 공식 문서 검증 전 Codex adapter를 구현 범위에서 제외한다.
  - MVP 선택지를 명시적으로 결정한다: 운영자 제공 API budget, 로컬 모델, LLM 없는 deterministic extraction demo, 또는 제한된 사전 계산 결과.
  - embedding도 별도 provider·모델·차원·비용·데이터 전송 경계를 결정한다.
  - provider 부재 시 기능별 degradation을 정의한다. 예: 검색과 원문 열람은 유지하되 AI 평가는 비활성.
- 검증:
  - 선택한 provider의 공식 지원 범위와 사용 조건을 기록한 ADR을 승인하고, credential 없는 환경·quota 초과·provider 장애에서 정해진 fallback을 테스트한다.

### DSR-009 — 적합성 판정의 의미와 오탐 방어 기준이 충분히 구체적이지 않음

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:75-85`
  - `docs/00-project-context.md:19-27`
  - `docs/03-test-plan.md:64-81`
- 실패 경로: 필수 자격 한 항목이 UNKNOWN인데 기술 역량 유사도만 높아 `SUITABLE`로 판정한다. 반대로 프로필 부재를 `UNSUITABLE`로 변환한다.
- 영향: 사용자가 법적 자격 또는 실제 참여 가능성을 과신할 수 있다.
- 수정안:
  - `SUITABLE`을 “확인된 범위에서 명시된 필수조건과 충돌 없음”처럼 제한적으로 정의한다.
  - 법적·행정적 필수조건에 UNKNOWN이 하나라도 있으면 `SUITABLE` 금지 등 상태 불변조건을 둔다.
  - requirement별 `SATISFIED`, `CONFLICT`, `UNKNOWN`, `NOT_APPLICABLE`을 먼저 계산하고 결과를 집계한다.
  - 화면에서 기술 적합성과 참가자격 검토를 분리하고 비대체 고지를 결과 근처에 배치한다.
- 검증:
  - 필수조건 UNKNOWN, 상충 근거, 오래된 프로필, 복수 조건 AND/OR, 예외 조항 표본으로 상태 불변조건 테스트를 작성한다.

### DSR-010 — 평가 계획에 데이터 구성·판정 기준·출시 임계치가 없음

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:52-55,70-73`
  - `docs/03-test-plan.md:64-81`
- 실패 경로: 작은 labeled set에서 임의 top-k hit 하나만 보고 retrieval 또는 분류가 충분하다고 선언한다. 쉬운 예제만 포함하면 필수 자격 누락 같은 치명적 false negative가 드러나지 않는다.
- 영향: 측정은 했지만 공개 데모 신뢰도를 보장하지 못하는 상태가 된다.
- 수정안:
  - corpus 출처·버전·라이선스, annotation 지침, reviewer 수, disagreement 처리, train/dev/test 분리를 정의한다.
  - AI/SW 관련성, 필수요건 추출, claim-evidence 연결, 최종 상태를 별도 평가한다.
  - 전체 정확도 외에 필수요건 누락과 근거 없는 결론에 더 엄격한 release gate를 둔다.
  - 정확한 수치는 실제 baseline 측정 뒤 확정하되, gate 결정 절차는 구현 전에 정한다.
- 검증:
  - 고정된 versioned evaluation set과 실행 결과에 commit/model/prompt/parser 버전을 남기고, 동일 구성 재실행 가능성을 확인한다.

### DSR-011 — 프로필 개인정보의 최소수집·보존·삭제·모델 전송 정책이 빠짐

- 심각도: **MAJOR**
- 근거:
  - `docs/01-requirements.md:30-37`
  - `AI_CONTEXT.md:30-37`
  - `docs/04-operation-and-deployment.md:43-45`
- 실패 경로: 사용자가 기업 등록번호, 담당자 정보, 내부 역량 자료를 입력하고 해당 내용이 장기 저장되거나 외부 LLM prompt로 전송된다. 계정 삭제 후 분석·embedding·로그에는 계속 남을 수 있다.
- 영향: 공개 포트폴리오 서비스가 필요 이상의 개인정보·기업정보를 보유하고 제3자 provider로 전달할 위험.
- 수정안:
  - MVP 프로필 필드를 비민감 최소 집합으로 고정하고 자유 텍스트를 제한한다.
  - 각 필드의 목적, 보존 기간, 수정·삭제, 계정 삭제 cascade, 로그 redaction을 정의한다.
  - LLM 전송 필드를 allowlist하고 전송 전 미리보기 또는 명확한 고지를 제공한다.
  - embedding·분석 snapshot·backup에서 삭제되는 시점과 방법을 정의한다.
- 검증:
  - 계정 삭제 후 profile, run, prompt record, vector, cache, export에서 데이터가 정책대로 제거되는지 확인한다. 민감 패턴이 로그와 provider request fixture에 없는지도 검사한다.

### DSR-012 — 운영 복구가 “문서화 예정”이며 데이터 손실 목표가 없음

- 심각도: **MINOR**
- 근거:
  - `docs/04-operation-and-deployment.md:31-33`
  - `docs/03-test-plan.md:83-93`
- 실패 경로: schema migration이나 parser 재처리 후 분석·근거 연결이 손상되지만 어떤 버전을 복구해야 하는지, 원천 데이터는 재수집 가능한지 판단할 수 없다.
- 영향: 공개 데모 장애 시 복구 시간과 데이터 손실 범위가 예측되지 않는다.
- 수정안:
  - MVP 데이터별 authoritative/rebuildable 구분, backup 범위, 최소 RPO/RTO, migration forward recovery를 정의한다.
  - raw source snapshot을 보관하지 않는다면 upstream 변경 시 재현 불가능성을 명시한다.
- 검증:
  - 임시 환경에서 backup/restore, migration failure, 애플리케이션 rollback과 DB 호환성 smoke test를 수행한다.

### DSR-013 — MVP가 한 번에 너무 많은 기술 요소를 요구함

- 심각도: **MINOR**
- 근거:
  - `README.md:47-60`
  - `AI_CONTEXT.md:20-22`
  - `TASKS.md:15-28`
  - `docs/02-architecture.md:44-46,123-133`
- 실패 경로: Google OIDC, SSE, LangGraph, pgVector, MCP, 문서 parser, 외부 API와 LLM을 동시에 구축하다가 핵심 시연 흐름이 완성되지 않는다.
- 영향: 포트폴리오가 넓지만 검증되지 않은 scaffold에 머물 가능성이 크다.
- 수정안:
  - 1차 vertical slice는 단일 사용자 또는 제한된 로그인, 고정 공고 fixture/소수 실제 공고, PDF 한 형식, deterministic 검색·추출, 동기 작업 상태 조회로 축소한다.
  - retrieval baseline으로 단순 full-text/section search를 먼저 평가하고 pgVector는 개선 근거가 있을 때 추가한다.
  - MCP와 LangGraph는 직접 함수/명시적 state machine보다 실제 경계 가치를 제공할 때만 채택한다.
- 검증:
  - 한 공고에 대해 원문→요건→프로필 비교→근거 표시가 end-to-end로 실행된 후 각 추가 기술의 개선 효과를 별도 기록한다.

## 의사결정이 필요한 미확정 사항·가정

다음은 확인된 결함이라기보다 구현 전에 답해야 할 결정이다.

1. Google 로그인은 backend BFF형 authorization code flow인지, SPA가 code를 받아 backend로 전달하는 방식인지.
2. 세션은 server-side opaque session인지 signed/encrypted cookie인지, 저장소와 폐기 전략은 무엇인지.
3. 나라장터 공고의 실제 natural key, 정정·취소·차수 관계, 첨부파일 획득 경로와 마감 timezone.
4. MVP가 저장할 프로필 필드와 공개·민감 데이터의 경계.
5. 원문 파일을 보관할지, hash와 파싱 결과만 보관할지 및 제3자 자료의 이용·보존 조건.
6. 초기 지원 문서 형식과 parser 격리 환경.
7. LLM과 embedding provider, 데이터 처리 위치, 비용 부담 주체, 장애 시 기능 축소 방식.
8. SSE가 정말 초기 MVP에 필요한지, polling으로 먼저 시작할지.
9. 분석 실행이 요청 생명주기 안에서 끝나는지, 별도 background execution이 필요한지.
10. `SUITABLE`이 기술 검토 결과인지 참가자격까지 포함한 제한적 표현인지.

## 작은 MVP 중심 재설계 방향

권장 첫 vertical slice는 다음 정도다.

- Google 로그인을 포함하더라도 먼저 OIDC/session ADR을 확정한다.
- 실제 확인된 나라장터 API 한 종류와 제한된 업무 구분만 지원한다.
- 공고 원천 snapshot과 normalized record를 분리한다.
- 첨부는 공식 allowlist의 PDF 한 형식, 낮은 크기 상한, 격리 parser로 제한한다.
- 참가요건을 항목별 `SATISFIED/CONFLICT/UNKNOWN`으로 표시한다.
- deterministic 키워드·규칙 검색과 근거 연결을 먼저 완성한다.
- LLM은 provider가 공식적으로 확정될 때 선택적으로 활성화하고, 없을 때도 검색·원문·수동 검토가 동작하게 한다.
- LangGraph, pgVector, MCP, SSE는 각각 실측된 필요성이 생길 때 추가한다.

## 선행 작업 상위 5개

1. **ADR-001 인증·세션 계약 확정**  
   OIDC flow, token 검증, cookie, CSRF/CORS, logout/expiry 및 권한 행렬을 포함한다.

2. **실제 나라장터 API read-only probe와 canonical data contract 작성**  
   식별자, 수정·취소, pagination, 날짜/timezone, 첨부 구조, 장애 형태를 실제 응답으로 확인한다.

3. **원문·파싱·요건·claim·evidence 버전 모델 확정**  
   분석 결과가 특정 원문 버전과 passage로 재현 가능해야 한다.

4. **안전한 문서 수집/파싱 threat model 및 제한 계약 작성**  
   URL·redirect·DNS, 크기, 압축, MIME, parser sandbox와 지원 형식을 고정한다.

5. **실행 가능한 LLM/embedding 및 비용 ADR 확정**  
   Codex/ChatGPT 연결을 추정하지 말고 공식 지원을 확인하며, provider 없는 MVP fallback과 평가 계획을 포함한다.
