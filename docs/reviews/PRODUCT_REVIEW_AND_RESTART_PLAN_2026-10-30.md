## 1. 결론: 어디에서 멈췄는가

**BID-06의 독립 정답 검수 도구까지 구현했지만, 실제 최신 RFP에 사람이 승인한 정답을 넣어 품질을 측정하는 단계에서 멈췄다.** 다음 기능 번호는 BID-07이지만 바로 시작할 상태는 아니다. 우선 최신 CI의 날짜 의존 실패를 정비하고 BID-06 실자료 검증을 완료해야 한다.

10월 19일 운영 인수 기록의 독립 승인 정답은 0건이다. 따라서 당시 실자료 정확도는 `NOT_EVALUATED`, 회사 적격·수익·인력/MM은 `UNVERIFIED`다. **이는 10월 30일 PC 실측 수치가 아니다.** 이번에는 사용자 PC·실제 RFP·회사 자료를 조회하지 않았다. 중단의 문서상 이유는 최신 공식 원본·차수 결속과 사람 정답 증빙 부족이며, 현재 자동 작업/프로세스의 가동 여부는 미확인이다.

기능 추가보다 먼저 제품의 핵심 질문을 닫아야 한다. **“우리 부서가 이 공고를 왜 검토해야 하며, 다음에 무엇을 확인하면 참여·보류·불참을 결정할 수 있는가?”** 지금은 검토 큐와 증거 보호가 강점이지만, 그 질문에 필요한 공고별 회사 증빙과 실측 품질이 아직 연결되지 않았다.

## 4. 발견 사항과 개선 판단

아래 P0/P1/P2는 재개 작업의 우선순위이며 보안/릴리스 결함의 심각도 등급이 아니다. 특히 F-03은 현재 보수적 평가 설계를 유지하면서 실측·표현을 개선하자는 제안이다.

### F-01 · P0 · 최신 CI가 날짜에 따라 실패한다 — 재현 확인

`local_app/test_procurement_filter.py:22`의 테스트는 마감 `2026-10-20 10:00:00` 공고를 `db.normalize()`에 넣고 `OPEN`을 기대한다. `dashboard_backend.normalize()`가 호출하는 분류 경로는 `procurement_filter.bid_window()`의 현재 시각을 사용한다. 10월 29일 CI와 이번 재실행에서 모두 `CLOSED`여서 실패했다.

**수정 방향:** 테스트의 관측 시각을 고정하고, 마감 전/정각/후와 KST 경계를 각각 검증한다. 필요하면 normalize의 시간 인자를 기존 호출과 호환되게 주입한다. 마감을 먼 미래로 옮기거나 실제 운영의 마감 차단을 완화하지 않는다. 기존 실패 때문에 뒤의 감사/backend 테스트가 실행되지 않으므로 첫 재개 작업으로 삼는다.

### F-02 · P1 · CI 아티팩트가 현재 실행 소스 전체를 담지 않는다 — 정적 누락 확인

`.github/workflows/sprint1-ci.yml`의 `local-python-bid-agent`는 파일을 수동 열거한다. `server.py`가 직접 import하는 `workforce.py`, `json_transaction.py`, `rfp_requirements.py`, `rfp_ground_truth.py`, `bid_readiness.py` 등 **19개 로컬 모듈**이 목록에 없다. 새 `frontend/public/rfp-ground-truth.js`도 누락된다. 기존 checkout 테스트와 업로드 성공만으로 독립 설치가 보장되지 않는다.

**수정 방향:** 기존 패키지 관련 도구/NOTICE 게이트를 먼저 확인하고 현재 배포 manifest와 연결한다. 비공개 데이터·키·캐시를 제외한 명시 manifest를 유지하되 의존 모듈/정적 자산 누락을 자동 검사한다. 빈 임시 폴더에 실제 패키지만 풀어 서버 시작·health/화면 자산·종료 smoke를 실행한다. 저장소 전체를 무차별 ZIP하지 않는다. 로컬 현재 운영이 고장 났다는 결론은 아니다.

### F-03 · P0 · 정확도 숫자의 의미를 좁혀야 한다 — 설계상 제한 확인

`rfp_ground_truth._counts()`는 **범주 + NFC/공백 정규화된 문구의 정확 일치**를 센다. 의미적 동등성, 법적 조건 충족, 회사 적격 정확도가 아니다. `evaluate()`는 승인 정답이 없으면 null이며 대표성은 `NOT_ESTABLISHED`, 전체 문서 정확도는 `NOT_EVALUATED`로 유지한다. 이 보수적 설계는 올바르다.

다만 현재 후보 표시 상한과 검수 범위 안에서 얻은 Recall을 “RFP 전체 요건 재현율”로 읽으면 제품 가치가 과대평가된다. **문구 분절 불일치 / 유형 오분류 / 추출 실패 / 표시 상한 / 실제 의미 누락**을 따로 기록해야 어떤 부분을 고칠지 알 수 있다. 표본에서 고득점이라는 이유만으로 자동 참여 가능 상태를 열지 않는다.

### F-04 · P1 · 자료 준비도와 공고별 판단 사이가 아직 비어 있다 — 코드/백로그 일치

`bid_readiness.assess()`는 자료의 존재·확인일·MM/원가 입력 상태를 검사하며 자격·기술·인력·수익은 모두 `UNVERIFIED`다. 기존 `operations.calculate()`는 견적 계산이지 공식 자격 확인이나 공고별 수익 보증이 아니다. **BID-07의 핵심은 증빙 연결과 검증일/유효기간/변경 무효화이며 새 종합점수 추가가 아니다.**

### F-05 · P2 · 후보 화면은 의사결정보다 상태 점검에 치우쳐 있다 — 소스 기반 UX 가설

`frontend/public/dashboard-live.js`의 후보 카드는 공고 ID와 상태·위험·미검증 문구를 보여주고 제목·기한·판단은 기존 상세로 연결한다. 오류/경합 방어는 유지할 가치가 있다. 다만 사용자가 후보를 비교하려면 상세 왕복이 필요할 수 있다. **이번에 브라우저 사용성을 실측하지 않았으므로 확정된 UX 결함이나 시간 절감 효과로 주장하지 않는다.**

개선 시 같은 snapshot의 공개 제목·발주기관·확인된 기한·현재 막힌 이유·다음 행동 하나를 보여주고, SHA/내부 상태 코드는 접는다. 기존 비식별 큐 API의 데이터 계약을 임의 확장하지 말고 같은 revision의 목록과 결합하는 방식을 먼저 검토한다. 새 UI는 합성 시안으로 사용자 검토 후 연결한다.

### F-06 · P2 · 최신 판단과 과거 실행 이력이 한 문서에 반복된다 — 문서 구조 확인

`AI_CONTEXT.md`, `CURRENT_STATE.md`, `TASKS.md`에 과거 미착수/NO_GO/완료가 누적되어 있다. 날짜순 최신 절이 우선이라는 규칙은 있으나 재개 시 혼동 비용이 크다. 이번에는 최상단에 본 검토 진입점을 연결한다. 후속 정리에서는 현재 상태표 1개와 과거 불변 기록 링크를 분리하되, 실패·승인 이력을 삭제하지 않는다.

## 5. 어디서부터 무엇을 어떻게 왜 할 것인가

## 6. BID-06을 끝내는 구체적인 첫 실험

1. **표본 선정표부터 만든다.** 시작 제안은 5~10개 공고이며 충분한 통계 표본이라는 뜻은 아니다. 텍스트 PDF/HWP/HWPX, 표·각주, 스캔/OCR, 정정 이력, 복수 첨부·표시 상한 사례를 구분한다. 없는 유형은 빠졌다고 기록한다. 사업 특성은 실제 사용 대상과 맞춘다.
2. **공식 최신성부터 확인한다.** 공고번호·차수·정정/취소·등록/제안 마감과 공식 첨부·SHA를 로컬에서 결속한다. 원본 부족은 추측하지 않고 보류한다. 공개 Git에는 원문·회사/개인정보·개별 파일 경로를 올리지 않는다.
3. **후보를 정답으로 복사하지 않는다.** 사람이 원본 페이지/표/각주/이미지를 먼저 검수해 참가자격·평가기준·과업범위 구절과 위치를 기록한다. 1~2개로 라벨 기준을 맞춘 뒤 평가용 표본을 분리하고, 규칙 튜닝에 쓴 사례와 holdout을 구분한다. 애매한 조건은 두 번째 검토/합의 이유를 남긴다.
4. **검수 범위를 명시한다.** 선택 페이지·실제 확인한 경로·미확인 페이지·파서/표시 제한·정답 개수를 기록한다. 원문에서 발견됐지만 후보에 없는 요건도 FN으로 포함한다. 범위 밖 문서까지 검수했다고 표시하지 않는다.
5. **수치와 실패 사례를 함께 본다.** 범주/경로별 TP·FP·FN과 분모, Recall/Precision/F1/누락률을 기록한다. 문구 정확 일치와 의미적 검토는 별도 결과로 유지하고 기존 지표를 사후 유리하게 바꾸지 않는다. 분모 0은 null이며 100%로 바꾸지 않는다.
6. **재검토 가능한 인수 기록을 남긴다.** 평가 소스 SHA·파서 버전·표본 선정 근거·검수일·가명 검수자 참조·오류 유형·미확인 범위를 로컬에 보존한다. 공개 보고에는 허용된 비식별 집계와 방법·제약만 남긴다.

첫 실험의 완료는 **성능 기준선과 오류 원인 확보**다. 제품 전체 정확도/대표성이나 BID-06 전체 완료로 자동 승격하지 않는다. 허용 가능한 필수조건 누락률·최소 표본 규모·품질 임계치는 baseline과 위험을 보고 사용자/업무 책임자가 확정한다. 현재 임의의 95% 같은 통과선을 만들지 않는다.

## 8. 효과 측정·비용·후순위

제안 지표: 공고당 검토 소요시간(중앙값과 범위), 원문으로 확인한 필수조건 누락 건수/검수한 조건 수, 보류 해소 시간, 정정 발생 후 재검토 누락, 판단 사유/증거 버전 연결률. 지금 baseline과 개선 목표치는 **미측정**이다. 수주율은 표본과 시장 요인에 좌우되므로 초기 제품 성능의 단독 지표로 쓰지 않는다.

개발 시간은 자료 상태에 따라 크게 달라진다. R0는 작은 테스트 수정 단위, R1은 1~2개 라벨 기준 맞춤 이후 표본 확대, R2/R3는 공고 하나의 수직 기능으로 잘라 진행한다. 원본 접근·회사 증빙·검수자 시간을 개발 완료일에 숨기지 않는다. AI 호출은 처음부터 모든 공고에 반복 실행하지 말고 현재 규칙 baseline에서 실제 누락이 확인된 범위만 검토한다. 외부 AI 자료 전송 동의·사용량 경계는 유지한다.

지금 뒤로 미룰 것: React/FastAPI 전면 이전, PostgreSQL/vector DB/MSA, 다중 모델 경쟁, 대규모 자동 요약, 로그인·공개 서비스, 자동 입찰. 기존 자산을 폐기하지 않으며 현재 병목 해결에 필요한 증거가 생기면 다시 판단한다. 유지보수 개선도 `dashboard-live.js` 전체 재작성보다 새 판단 카드/상세 섹션의 경계 분리부터 적용한다.
