# RFP 3유형 분류 Precision/Recall/F1 평가 프로토콜 (2026-10-16)

## 목적과 구현 경계

- 평가 코드: `local_app/rfp_taxonomy_benchmark.py`
- 합성 회귀: `local_app/test_rfp_taxonomy_benchmark.py`, 기존 `test_rfp_requirement_taxonomy.py` 사례 재활용
- 평가 대상은 **추출된 RFP 텍스트 한 줄에 독립적으로 지정된 참가자격/평가기준/과업 라벨**의 예측 일치 여부뿐이다.
- 실제 RFP 원본 전체 필수요건 수, 다운로드/파싱되지 않은 내용, PDF 표/각주/페이지, 전체 요구사항 누락률 또는 법적 입찰 적격성을 **측정하지 않는다**.
- `evaluate(lines, origin=...)`는 메모리 객체만 받고 TP/FP/FN과 3범주별 및 micro Precision/Recall/F1만 반환한다. 원문/공고 ID/파일명/라벨별 사례를 결과에 넣지 않는다.
- `SYNTHETIC`은 코드 작성자가 정의한 합성 정답, `DECLARED_INDEPENDENT_HUMAN`은 호출자가 수기 독립 라벨이라 선언한 값이다. 호출자는 근거를 별도 관리해야 하며 코드가 독립성·신뢰성을 검증하지는 않는다.
- 정답 양성이나 예측 양성이 없어 분모가 0인 지표는 1.0으로 가정하지 않고 `null`로 반환한다.

## 실제 정확도 평가를 위한 후속 데이터 수집 절차 (현재 미실행)

1. 먼저 사용 가능한 공식 원문과 실제 추출 결과의 상태를 조사한다. 현재·정정/취소·STALE 구분, 원문 PDF/HWP/HWPX/스캔, OCR 적용/미적용, 표/각주, 44,000자 절단, 첨부 2개 초과를 **별도 층**으로 기록한다.
2. 공고/문서 단위 표본을 선정한 뒤 단순 양성 후보만 뽑지 않는다. **매칭되지 않은 줄을 포함**해 추출된 줄을 독립적으로 전수/표본 라벨링한다. 표본 추출 규칙과 제외율/중복/문서별 줄수를 기록한다.
3. 참가자격, 평가기준, 과업을 다중 라벨로 지정한다. 제목·평가용 사업 소개·과업 계약변경·실제 시스템 개발이 섞인 문장은 각각 근거 구간과 다중 라벨 검토 지침에 따라 사람이 판정한다. 모호한 문장은 합의 절차를 별도 기록한다.
4. 규칙 개선에 사용한 개발 라벨과 **최종 독립 검증 라벨을 공고 단위로 분리**하고, 가능한 경우 라벨러 간 불일치/재판정과 원본 문서 SHA의 별도 내부 근거를 보존한다.
5. 평가 도구로 각 분류의 TP/FP/FN 및 micro 지표를 산출한다. 카테고리별 표본 수·실측 음성 사례 수·원본 형식별 제한을 함께 보고하며, 통계적 대표성이 없다면 모집단 정확도를 주장하지 않는다.
6. **원본 전체 요구사항 Recall**을 측정하려면 추출된 한 줄 평가 외에 원본 PDF/HWP의 페이지/표/각주/스캔까지 별도 사람 라벨링하고, 파서·추출·규칙·상한의 단계별 손실을 각각 대조해야 한다. 현재 Stage 1 평가 도구는 이 검사를 하지 않는다.

## 비공개 데이터 보안

- 공개 GitHub에는 실제 원문, 직원 정보, 자격·원가, 공고별 SHA/파일명 및 독립 라벨의 원문을 올리지 않는다.
- 실제 데이터 라벨링은 권한이 있는 Windows 환경 내부에서만 별도 승인과 보안 정책에 따라 수행하며, Codex/외부 모델로 자동 전달하지 않는다.
- 평가 코드는 읽기/쓰기/외부 통신이 없고, 문자열·라벨 검사를 수행한 후 숫자형 집계만 반환한다.
- 실제 검증 작업이 완료될 때까지 `REAL_RFP_PRECISION_RECALL=NOT_MEASURED`이며, 합성 사례 100% 결과를 실데이터 수치로 표현하지 않는다.
