## 가장 중요한 심각도 및 권고 조정

### R-01 사용자별 ChatGPT/Codex 인증·비용

- 1차 의견: `F-01 BLOCKER`, 개인별 API Key 또는 운영자 유료 API Key 이외의 경로가 없다고 기술.
- 2차 의견: `DSR-008 MAJOR`, 지원 여부와 비용/embedding 경로를 공식 확인한 뒤 확정하도록 권고.
- 조정: **확정된 BLOCKER가 아니라 `MAJOR / 실현 가능성 및 공개 배포 진입 조건 미결`로 분류**.
- 근거: OpenAI 공식 [Sign in with ChatGPT 오픈소스 안내](https://developers.openai.com/siwc/token-sharing-open-source)는 사용자 ChatGPT 플랜으로 적격 추론을 수행하는 OAuth 경로를 설명한다. 따라서 "항상 사용자 API Key가 필요하다"는 절대적 주장은 사실이 아니다.
- 제한: 같은 공식 문서는 **원격 호스팅 또는 유료 앱**의 경우 별도 관심/참여 신청을 안내한다. 현재 계획된 공개 호스팅 웹서비스가 별도 승인 없이 그 경로를 사용할 수 있다는 근거는 아직 없다.
- OpenAI [API/ChatGPT 결제 안내](https://help.openai.com/en/articles/9039756-managing-billing-settings-on-the-chatgpt-web-and-api-platform)에 따르면 일반 API 비용은 ChatGPT 구독과 별도다.
- 처리 방안: 요구사항 `REQ-COST-001`(별도 종량제 API를 MVP 필수조건으로 삼지 않음)을 유지하고 `ADR-004`에 적용 가능성·신청 요건·사용자 권한/한도·실패 시 기능 축소 경로를 결정한다. 무단 구독 공유, 사용자 비밀번호/세션 수집, 임의 API Key 수집은 채택하지 않는다.
- 상태: `PENDING_DESIGN`. 실제 공식 사용자 플로·적용 자격 테스트 전에는 ChatGPT/Codex 연결을 완료로 표시하지 않는다.

### R-02 SSE 인증 방식

- 1차 의견: `F-05 MINOR`, URL에 1회용 티켓을 넣어야 한다는 제안.
- 2차 의견: `DSR-002/DSR-003 MAJOR`, 인증/인가와 각 `analysis_id`의 소유권 검증 강화.
- 조정: **별도 티켓은 필수가 아니라 `QUESTION / ADR-001의 구현 선택`**. 동일 출처의 HttpOnly 쿠키 기반 세션을 이용하는 SSE도 가능하며, 로그인 인증만으로는 충분하지 않고 분석 실행의 소유자 검증과 재연결 검증이 필요하다.
- 처리 방안: 쿠키·CORS·CSRF 정책과 SSE 연결·재연결·취소의 서버 측 소유권 검증을 명시한다. 토큰이나 인증정보를 URL에 넣지 않는다.

### R-03 공통 보안·정확성 지적

독립 리뷰 간 내용이 일치하며, **구현 전에 설계 수준에서 해결할 `MAJOR` 후보**다.

1. `F-02 / DSR-002`: Google OIDC 흐름, ID Token 검증, 세션 수명, CSRF/CORS와 테스트
2. `DSR-003`: 프로필·분석·질문·SSE·취소 API에 대한 객체 소유권 행렬
3. `F-04 / DSR-004`: 공고 natural key, 개정/정정/취소, 마감 시각과 최신성
4. `F-03 / DSR-005`: 첨부파일 SSRF·redirect·DNS·MIME·크기 제한, parser 격리·압축 제한
5. `DSR-006`: 문서 원본 버전부터 요건·최종 결론까지 추적 가능한 근거 ID/해시 계약
6. `DSR-007`: Agent 반복·비용·사용량 예산, 취소, 중단, 사용자 질문 만료, 도구 권한
7. `DSR-009`: 참가자격과 기술 적합성을 분리하고 UNKNOWN일 때 적합 확정 방지
8. `DSR-010`: 추출/분류/근거 연결의 버전 관리된 평가 샘플과 출시 판정 절차
9. `DSR-011`: 사용자 입력·기업 프로필 최소수집, 삭제, 외부 모델 전송 및 로그 정책

나머지:
- `DSR-001`의 `READY WITH ASSUMPTIONS` 표시와 현재 게이트 `HOLD` 불일치는 문서 상태를 먼저 바로잡는다.
- `DSR-012` 복구와 `DSR-013` MVP 기술 범위는 초기에 단순화하고 공개 배포 전 점검한다.
- 실제 공공 API 스키마/첨부 형식, 모델 비용 및 제공자 지원 상태, 취약점 재현과 테스트 결과는 아직 측정하지 않았다.

## 후속 작업 순서 및 완료 기준

1. **P0 인증/사용자 경계**: ADR-001로 OIDC 세부·서버 세션·객체별 권한·SSE 정책과 교차 사용자 테스트 계약 정의
2. **P0 공고 데이터 계약**: 공식 API 실제 읽기 전용 표본 확인, 식별자·정정·취소·수집 상태·시간대 정의 (계정/서비스 키는 기록 금지)
3. **P0 문서·근거 계약**: URL/file threat model, PDF 우선 지원 범위, 안전한 파서 경계, 원문 버전과 요건/근거 관계 정의
4. **P0 판단·작업 수명주기**: 참가자격 불확실성, AI 실행 한도·취소·오류 상태, 평가 샘플 설계
5. **P0 LLM 경로**: 오픈소스용 SIWC와 원격 호스팅 자격을 분리해 ADR-004 검증, 별도 종량제 비용 없이 시연 가능한 fallback 결정
6. **P1 최소 단위 MVP**: 위 P0를 해결한 뒤 제한된 공고와 안전한 문서 포맷으로 검색→근거→조건 검토를 먼저 시연; LangGraph·pgVector·MCP·SSE는 유의미한 필요성을 입증하여 순차 도입
